# Tool bindings

Users edit through modules; the engine runs operations, darktable-style algorithms, at fixed pipeline positions (architecture decision 4). A binding connects the two: a control's value becomes operation parameters, directly or through a transfer function. The UI, presets, edits and MCP all work at module level.

In the first pass each module is darktable's own (decision 2: rewrite first, improve later): one module per darktable module Apertrust includes, under darktable's name, its parameters the controls under darktable's labels, both of darktable's white balances among them, White balance over `temperature` and Colour calibration with its CAT tab (decision 27). `docs/modules/README.md` lists the modules by side panel tab, with their operations, slots and owners, and holds the rules every first-pass module follows (cited below as "modules rule N"; "rule N" alone is one of this skill's numbered rules under How a control maps); each module's page beside it holds its controls, sliders and invariants. Once the whole project is migrated, Apertrust evolves on its own.

These rules are how a module keeps principle 5 of `docs/principles.md` (decision 1), "every control keeps to what it says": each control is a darktable parameter and does what darktable's does, checked against darktable; a module that is off leaves the photo untouched (decision 32); no control's effect depends on a hidden setting or on the order controls were used in; and a slider will behave the same on a layer as on the whole photo. Auto, like every goal the editor works towards, moves only the controls the user has not kept (principle 7).

## Rules

- **One owning module per engine parameter.** Depth comes from inside that module, its own tabs and collapsible groups (decisions 2 and 29), never from a second module. A module declares what it owns (`Module::owns`); a test across the built-in modules refuses a parameter owned twice, and at run time the session reports such a module as failed and leaves it out.
- **A module that is off is a no-op, exactly** (AGENTS.md; decision 32; modules rule 4). A module whose operation every photo runs is untouched at its defaults: it sets no parameter there, so it leaves the plan, the cache keys and the frame as they were, byte for byte. "Its defaults" are each control's: the definition's, or the operation's for the photo where they come from it (as shot, the raw's own levels). **A module darktable leaves off on a new photo is switched** (decision 32, planned): `Definition::switched`, held by `check::accept` to own no parameter of an operation every photo runs; its controls default to darktable's, which `check::switched_defaults` holds to bind its operations' defaults exactly; it is off until a command writes one of its controls (`SetControl` on a control or a coordinate, `ApplyPreset`, Auto), whatever the value, then on, the edit holding `enabled` beside its values (`apertrust:enabled="true"`), its operation planned while it is on and its binding given its values off its defaults, possibly none; `ResetModule` turns it off, `ResetControl` and `Keep` never turn it on and leave an on module on. A module always on that drives an optional operation (`testing::Sample`) keeps the rule that the operation is planned while its binding sets it. Its invariant rows: off renders as no edit, exactly; on at darktable's defaults binds the operation's defaults exactly; the first step, the module on at darktable's defaults, is darktable's behaviour, measured and reported without a bound; a move then `ResetModule` renders as no edit, a move then `ResetControl` as on at darktable's defaults; an older edit, migrated, binds what it bound; no row at zero for its controls. Nothing in the panel shows the off state but the reset's availability and the screen reader's "Not applied" (`ui-conventions`).
- **Sliders are darktable's** (decision 30; modules rule 3): every built module's slider as darktable's `gui_init` sets it, its hard range the control's, its soft range the track's span at rest, its factor and offset, digits and step, held by a test per module (How a control maps, 1; Testing a module).
- **Parameters with no editing meaning get fixed defaults**, documented in the port spec's tool binding notes.
- **Module values are what an edit stores**, with a module version; operation parameters are derived from them and never stored. A new module version with a migration (`Module::migrate`) keeps old edits' look. It is needed for a changed binding or meaning, a control or an option removed or renamed, a range narrowed or a default changed. Adding a control or an option, porting one or widening a range needs none: a build without it opens such an edit for viewing only (decision 48; The edit, below).
- **Header buttons**: every module has collapse, reset and presets, with no options button and no Auto button; no Advanced controls toggle (decision 29).
- **Background only or layers**, as the Layers column of `docs/modules/README.md` says for each module (modules rule 11).
- **The raw stage's modules are darktable's.** Raw-stage operations run before demosaic at full resolution, so a drag there re-runs demosaic (decision 12). White balance is darktable's white balance over `temperature`, so its drag does too, its frame time to be measured (decision 27); raw black and white levels, highlight reconstruction and demosaic stay in their own modules, and capture sharpening in Demosaic. The raw stage exports no derivatives (decision 21), so no Auto or matching fits a raw-stage control: the light is fitted through Colour calibration's `x` and `y`.

## How a control maps (decision 2)

A module mirrors one darktable module. `docs/modules/README.md` lists each with its darktable module, operation, slot and owners, and its page records darktable's labels, parameters, tabs, sliders and presets. Follow them, and update both with the module. **Who decides:** whatever follows from mirroring darktable, or is technical, is the architect's to decide and record; ask the user only about a deviation from the mirroring rule, product scope darktable does not cover (layers and masks, the library, export, AI), or a blocker.

1. **One darktable parameter per control,** under darktable's label and range, with at most a fixed change of unit (a percentage for a factor, degrees for radians) or an exact change of coordinates where darktable's own slider shows one (AgX's pivot in EV against the range). No control sets several parameters (modules rule 3). **A slider is darktable's:** the control's range is darktable's hard range in the units its slider shows (the params' `$MIN` and `$MAX`, times its factor, plus its offset), the row's soft range darktable's (`Slider::soft`, from `dt_bauhaus_slider_set_soft_range`), the row's decimals its digits and the control's step its `dt_bauhaus_slider_get_step` over the soft range. Each module's table records them against darktable's `gui_init`, and a test in its source holds the definition to it through `testing::slider_differences`, which finds no difference in any built module, AgX's pivot compared at its defaults and at other input ranges (decision 30; `docs/modules/README.md`, Sliders against darktable; `docs/modules/agx.md`). **A range that follows other controls** (decision 30): where darktable's `gui_changed` moves a slider's range with other controls (AgX's pivot over black to white relative exposure, its step darktable's for the width; crop's margins, each soft bound 0.01 from the opposite one), the module gives it through `Module::range(control, values)`, reading the module's values, never its own control's value, and not the photo. The definition's range is then the widest any values give, and its soft range and step those at the module's defaults. The session reports it with each number (`ControlState::range`), refuses a command outside it, and clamps a value a moved range leaves outside to the nearer end, stored and kept in the same change, as darktable's AgX `_update_pivot_x` and bauhaus's hard range do; a moved soft range keeps the value. Never state the clamp as a follow write too: the range says it once.
2. **A module that is off is untouched** (decision 32; modules rule 4). A module over an operation every photo runs starts at the photo as first shown, the operation's defaults for the photo. A module darktable leaves off on a new photo is switched: its controls start at darktable's defaults, it is off until one is written and then on with them, and its reset turns it off; darktable's defaults are no presets, and a value where the operation changes nothing is no untouched state.
3. **darktable's page, as darktable has it** (decisions 2 and 29; modules rule 5): its main page in darktable's order; each collapsible section a collapsible group at darktable's place, holding controls, never another group; every tab a content tab in darktable's order, masking, masks, options and advanced included. There is no Advanced controls toggle and no Basic/Advanced split. Every control darktable shows is a control, ported or not, an unported one drawn disabled. A row darktable shows only for one mode, or while another control holds a value, follows it; where darktable shows one parameter under two labels by mode (local contrast's `sigma_r`), or under conditions one `Row::When` cannot join (highlight reconstruction's Noise level, under guided laplacians and under segmentation based with a rebuild mode), the control has one row per mode, one shown at a time.
4. **A lossless view may be a second row** (decision 31; modules rule 6): where darktable shows the same stored values twice (colour calibration's illuminant as hue and chroma, white balance's coefficients as temperature and tint; the tone equalizer's bands as a curve, the identity view, which is a custom row naming the bands themselves, `Widget::Equalizer`, with no coordinates), the second is a view, an exact, invertible change of coordinates, with fewer coordinates than controls where darktable's model drops a scale, as temperature and tint drop the coefficients', `unview` then writing them as darktable's GUI does, normalised (decisions 27 and 31): the definition declares it (`View`: its id, the number controls it covers, its `Coordinate`s with range, step and unit), a `Row::Slider` names a coordinate, and the module implements `view` and its exact inverse `unview`. Its coordinates are addressed like controls in `SetControl`, `ResetControl` and `Keep`, the session holding the view's other coordinates through a gesture and reporting every coordinate (`CoordinateState`); nothing is stored under them, and marks and reset belong to the stored controls (`docs/modules/README.md`, Lossless views; `docs/engine.md`, Preset rows and lossless views). This is built in the engine and in the panel, `testing::Sample`'s `pair` the worked example: the app calls `view` and `unview` on its pending values (`modules::Pending::show`), so a drag follows at once, which is one more reason they must stay pure and read only the view's controls and the image context; the session's `Photo` carries the photo's image context, so a view may read the camera, as White balance's reads its colour matrix, and the app computes it with the same context as the session.
5. **Presets are darktable's** (modules rule 7), in the header's presets menu, applied by the session as one change; its auto-applied workflow presets are Apertrust's defaults already. A preset needing a parameter the module fixes, or a mode not ported, is left out.
6. **A choice lists darktable's options for the photo** (decisions 29 and 30; modules rule 8); those its operation does not port are drawn disabled and refused as commands.
   - **The definition** holds every option darktable lists on some photo, each once, with a permanent id. An option darktable lists on no photo, kept only for its old edits (highlight reconstruction's reconstruct colour), is left out.
   - **`Module::options(control, image)`** gives the ids this photo lists, in the definition's order, as darktable's `gui_init`, `reload_defaults` or `update_profile_list` build its list: demosaic's sensor's methods, as shot in camera only on a colour raw. Provided: every option. Built in the session, the edit, the CLI and the panel, `testing::Sample`'s method the worked example: camera listed only on a photo that records a bias.
   - **The session** reports them (`ControlState::options`), refuses `SetControl` with any other (`EditError::NotListed`), and reports a choice whose photo lists only the option it holds as unavailable.
   - **An edit from another photo** may hold an option this photo does not list. It is kept, pasted as it is, never view-only, and rendered as darktable's darkroom renders that photo: the operation's fallback where darktable's `commit_params` falls back; the binding writing darktable's correction where only its `gui_changed` makes one (highlight reconstruction's guided laplacians on a non-Bayer raw). The module's table holds that in an invariant row, as Demosaic's D1.
   - `options` reads only the photo; a list that follows another control is a row per mode (`Row::When`).
   - **A whole control can be unported too** (`Control::unported`, as Exposure's Highlight preservation mode, Percentile and Target level are): it takes only its default, any other value refused as an unported option is, so no edit stores a value the render ignores and nothing migrates once it is ported, and the session reports it unavailable, so it is drawn disabled. Its parameter stays in the operation's schema at the value rendered, owned by the module, the operation refusing any other. A control of a method not ported may own no parameter until the method's port adds it, since a port takes a method's parameters with the method (`port-module`, What to port): Highlight reconstruction's segmentation based and guided laplacians controls take darktable's defaults with no parameter in `highlights`' schema yet. A port takes an alternative mode only when a module needs it or the user chooses it.
7. **Both white balances are darktable's** (decision 27; modules rule 2): White balance over `temperature`, its id `temperature`, its Settings a preset row over the coefficients and `preset`, temperature and tint a view of the coefficients (`docs/modules/white-balance.md`); Colour calibration with its CAT tab, adaptation first, hue and chroma a view of `x` and `y` (`docs/modules/colour-calibration.md`). A preset row is never stored, its label the option whose values the controls hold, Custom otherwise, or a module's own fallback where `matching` is overridden (White balance's user modified). A preset row is declared in the definition (`PresetRow`: its id, option ids and the controls every option writes) and drawn by `Row::Preset`; the module gives each option's values for the photo with `preset`, `None` for one the photo cannot have, and `matching` says which option the values hold, exactly as provided; `ApplyPreset { module, preset, option }` applies one as one change and one history step, each control it sets kept (`docs/engine.md`, Preset rows and lossless views). All of this is built, `testing::Sample`'s `look` the worked example, and the panel draws it (`ui-conventions`, A preset row). **Planned (decision 27):** a preset row may list options per photo after its own, under a heading with the camera's maker and model (`PresetRow::camera`, `Module::listed`, in the photo's order: White balance's camera presets, darktable's `wb_presets.json` entries the image context carries, `Camera::white_balance_presets`), each also an option of the control the row writes with a permanent id, so an edit stores a camera preset by darktable's name, never its position in the list; and may take a tuning addressed like a control and never stored (`PresetRow::tuning`, `Module::tuning`: Finetune), `ApplyPreset` applying an option at the row's tuning and `SetControl`, `ResetControl` and `Keep` on the tuning's id applying the matching option at a whole tuning, with no follow writes, as darktable's `_preset_tune_callback` serves its list and its slider alike. Finetune is no lossless view: its inverse needs the chosen preset, its range the camera, and its reset is the preset's untuned entry, not the module's defaults.
8. **Follow writes** (decisions 27 and 31; modules rule 13): where darktable's GUI writes other parameters with a control to keep one quantity consistent (colour calibration's illuminant writing `x`, `y` and the correlated colour temperature; white balance's coefficients writing `preset` user modified), the module gives them through `Module::follow(control, values, image)`, pure, and the session applies them in the same change and history step, each kept, never rewriting the control the command set; a reset is a change to the default with its follow writes (`docs/engine.md`, Preset rows and lossless views). Controls of one quantity then set it last-wins, as two views do; controls of different quantities must still commute, and a write between two quantities stays refused (decision 30), but where one's range follows the other and a move clamps it (rule 1, decision 30). Never mirror darktable's session memory, a value its GUI keeps that no edit stores (the last daylight temperature, the user-modified coefficients): principle 5 rules out a hidden setting. Built with Colour calibration's CAT tab: `Edit::follow`, which the session runs inside each `SetControl` and `ResetControl`, never `ApplyPreset`, whose option writes the module's own values for every control its row names, as darktable's `_preset_tune_callback` writes without `gui_changed`, so a row names, and its options write, every control a follow write would otherwise keep in step (White balance's Settings writes all four coefficients and `preset`), refusing the whole change with `EditError::FollowFailed` when a write is wrong; `check::sweep` holds every module's writes to its controls and their ranges, and `testing::Following` is the worked example for other crates' tests.

A parameter no control exposes is fixed by the binding (with the reason, in the port spec's Owner column), left at darktable's default, or not ported; it still has its one owning module, which lists one it owns in `Module::fixed`, so a request to set it at operation level is refused as fixed by the module (`EditError::Fixed`). The module's id is its operation's (`exposure`, `toneequal`, `colorbalancergb`, White balance's `temperature`; modules rule 1). The built Tone curve's `tone_curve` is the exception until it becomes RGB curve, `rgbcurve`, and joins `RETIRED`.

**No Advanced controls toggle** (decision 29). Tabs are content tabs only: a curve's channels, colour balance rgb's master and 4 ways, colour calibration's R, G and B.

## A module (decision 28)

A module lives in `crates/modules/src/<name>.rs`, implements `Module` and joins `MODULES`; in the app it joins the side panel tab of darktable's group in the scene-referred preset, at its place in darktable's order, the last in the pipeline at the top (`TAB_MODULES`; decision 38; `docs/modules/README.md`, The modules by tab), a module darktable puts in no group joining the group darktable's other layouts give it (In no group there); a test holds each tab's list to `OPERATIONS` reversed and every built module to one tab. Its files are named by the module's English name, not its id: the source and its tests in snake_case (`crates/modules/src/colour_balance_rgb.rs` and `crates/modules/tests/colour_balance_rgb.rs` for `colorbalancergb`, whose id is its operation's; `exposure.rs`, `tone_curve.rs`), its table in kebab-case (`docs/modules/colour-balance-rgb.md`). `apertrust-modules` depends on `apertrust-plugin` and `apertrust-color` (the Tone curve's curve maths; White balance's maths later): never egui, wgpu, the engine or an operation crate. It names operations and parameters by id.

```rust
pub trait Module: Send + Sync {
    fn definition(&self) -> &'static Definition;
    fn defaults(&self, image: &ImageContext) -> Controls;    // provided: the definition's
    fn owns(&self) -> &'static [Owned];                      // every parameter it owns
    fn fixed(&self) -> &'static [Owned];                     // provided: none; owned, no control
    fn bind(&self, values: &ModuleValues, image: &ImageContext, base: &Base)
        -> Vec<Setting>;                                     // empty at the module's defaults
    fn available(&self, control: &str, values: &Controls, image: &ImageContext)
        -> bool;                                             // provided: true
    fn options(&self, control: &str, image: &ImageContext)
        -> Vec<&'static str>;                                // provided: every option (decision 30)
    fn range(&self, control: &str, values: &Controls)
        -> Option<Range>;                                    // provided: the definition's; a number's range, track and step (decision 30)
    fn curve(&self, control: &str, values: &Controls)
        -> Option<Box<dyn Fn(f32) -> f32>>;                  // provided: None, straight lines
    fn curve_width(&self, control: &str, values: &Controls)
        -> Option<f32>;                                      // provided: None; a band graph's reach
    fn preset(&self, preset: &str, option: &str, tuning: i32, values: &Controls, image: &ImageContext)
        -> Option<Controls>;                                 // provided: None; at the row's tuning (decision 27, planned)
    fn listed(&self, preset: &str, image: &ImageContext)
        -> Vec<&'static str>;                                // provided: none; a preset row's options the photo lists (decision 27, planned)
    fn tuning(&self, preset: &str, values: &Controls, image: &ImageContext)
        -> Option<Tuning>;                                   // provided: None; a preset row's tuning, its range while shown (decision 27, planned)
    fn matching(&self, preset: &str, values: &Controls, image: &ImageContext)
        -> Option<&'static str>;                             // provided: the first option equal exactly; None: Custom
    fn view(&self, view: &str, values: &Controls, image: &ImageContext)
        -> Option<Vec<f32>>;                                 // provided: None
    fn unview(&self, view: &str, coordinates: &[f32], image: &ImageContext)
        -> Option<Controls>;                                 // provided: None; view's exact inverse
    fn follow(&self, control: &str, values: &Controls, image: &ImageContext)
        -> Controls;                                         // provided: none; darktable's GUI's other writes
    fn migrate(&self, from: u32, values: ModuleValues) -> ModuleValues;  // provided: unchanged
}
```

Override `defaults` only for a default that comes from the photo, `available` for a control that can change nothing on some photos (decision 30) (Exposure's Use camera bias on a photo with no bias) or while another of the module's controls holds a value, as darktable's `gtk_widget_set_sensitive` in `gui_changed` says (vignetting's width/height ratio while automatic ratio is on; decision 30), which the panel then draws disabled while it still takes a value, the session recomputing it after each change, `options` for a choice darktable lists per photo (rule 6; decision 30), `range` for a number whose range, track or step darktable's `gui_changed` moves with other controls (rule 1; decision 30; AgX's pivot), `curve` for a curve whose operation does not join its points with straight lines (decision 31): its output at an input on the row's axes, for the values the panel shows, so the curve drawn is the curve rendered, held to the kernel by an invariant row (the Tone curve's `LumaCurve` and T4), or the curve a band graph draws through its bands, named by its first (the Tone equalizer's, its operation's own curve from `apertrust-color`, flat while the module plans nothing, `None` where the fit fails), `curve_width` for a band graph's drag, the width σ of the Gaussians that curve is a sum of, `preset` for a module that declares a preset row: each option's values for the photo, at the row's tuning where it has one, one for each control the row writes, `None` for an option the photo cannot have, `listed` and `tuning` for a row whose options the photo lists or which takes a tuning (decision 27), `matching` only to compare in a precision of the module's own, `view` and `unview` for a module that declares a lossless view: its coordinates for the controls' values, every control the edit's over the defaults, and their exact inverse, the session refusing what it gives outside a control's range, `follow` where darktable's GUI writes other controls with one (rule 8; Colour calibration's illuminant), and `migrate` from a module's version 2 on. `Sample` in `crates/modules/src/testing.rs` shows the shape: a control written over `base`, one that adds an optional operation, one that sets nothing while another is at its default, and one, coarseness, unavailable unless others hold values, size coarse and grain on (decision 30); `available` reads every control, the edit's over the defaults, and stays pure, since the app calls it on the values it shows before the session reports them. Its brightness adds EV to `exposure.exposure` with `transfer::Linear::over`: the photo's default plus the value, as darktable's exposure slider writes it and Exposure follows (decision 30). `testing::Faulty` is a binding that misbehaves on purpose, for the tests that it is left out.

**The definition is static data:**

- the module's id (snake\_case ASCII, permanent: it is in every saved edit, the CLI and scripts), its version (1 to start), whether it works on layers, whether it has Auto, and, planned, whether it is switched (`Definition::switched`, decision 32: true for a module darktable leaves off on a new photo);
- its **controls**, what the edit stores: an id (snake\_case, permanent), a kind (a number with range, step and default, the range the widest any values give where `range` moves it, decision 30; a choice with option ids and a default; a boolean; curve points), a unit, and whether it is unported, taking its default only (rule 6 above). A curve control stores only the points between its ends, (0, 0) and (1, 1), up to 18 of them, 0.0025 apart and as far from the ends; the binding adds the ends, so an edit keeps its meaning whatever the handles come to drive (decision 31);
- its **tabs**, content tabs only, each with its **rows**, and its **collapsible groups** (`Row::Group { id, rows }`, a title id and rows, never another group; decision 29), with no Advanced rows, and rows shown under every tab before or after the tab's (`Definition::before` and `after`), how the panel shows the controls: a slider (decimals, darktable's soft range, the track's span at rest inside the control's range, track, fill or not, quad: picker, showmask or Auto), a choice (list or segmented; every option darktable lists on some photo, those not ported in `ControlKind::Choice`'s `unported`, drawn disabled and refused as values, so never the default and never segmented; one whose options vary between photos a list too, decision 30), a toggle, a group label (`Row::Label`), or a custom widget from the design system's closed registry naming the controls it edits, the equalizer (`Widget::Equalizer`) a second view of number controls with rows of their own, as the Tone equalizer's graph is of its bands; and a **preset row** (White balance's Settings), with no control of its own: its options each write several of the module's controls, given by a pure provided method of `Module`, and the session applies one as a single change and reports which option the values match (`Module::preset` and `Module::matching`, and `ApplyPreset`, in `docs/engine.md`'s Preset rows and lossless views; darktable's presets in the presets menu go through the same command); and a **view row**, a `Row::Slider` naming a coordinate of one of the definition's views (decision 31; How a control maps, 4); the definition's `presets` and `views` hold what those two rows show; and a **tool's setting**, one of darktable's own settings for a tool that no edit stores (modules rule 12: the colour checker's chart, an area mode), `Row::ToolSetting` with its kind and no control, drawn disabled at darktable's default until the tool comes; and an **action**, one of darktable's buttons, which writes controls and is never stored (modules rule 10: AgX's Auto tune levels and Set from above), `Row::Action` with its id and no control, its words `module-<module>-action-<action>-label`, `-full` and `-promise`, drawn disabled until its tool comes, when it becomes a command; then the setting is declared in the settings schema with `owner = "module:<id>"` and the row names the static generated for it in place of its kind (decision 43). Each control appears in one row, or only in the rows of its lossless views (decisions 29 and 31); a number control may also appear in one equalizer's row, the one widget allowed as a second row beside a control's own until another needs it. One tab without a title draws no tab strip. Rows may follow another control, a choice or a toggle, for the values they show for (`Row::When { control, is, rows }`, `is` as the control writes its values; decision 29), shown wherever the rows are or on another tab outside any group or mode, as the tone equalizer's Mask contrast compensation follows its filter; a control darktable labels differently by mode has a row in each mode's `When`, no two shown at once, with words of its own (`Slider::label`). `Definition::check` holds all of it, so `check::accept` refuses a module that breaks it. Visibility, disabled options and the groups' open state are the renderer's, never in the edit.
- its **readouts** (decision 19, planned; `docs/engine.md`, Readouts): `Definition::readouts`, each `Readout { id, operation }`, a readout of one of the operations it owns parameters of, which that operation's manifest lists, as the tone equalizer's `mask_histogram` of `toneequal`; `check::accept` refuses any other. A custom row names the readout it draws behind its controls. A readout stores nothing and binds nothing: the session measures it and clients ask for it by module and readout id, never by operation.

**Words are message ids that follow from the ids**, never English in the definition, a fixed word before each id so none collides: `module-<module>-title`, `module-<module>-auto`, `module-<module>-tab-<tab>`, `module-<module>-group-<group>`, `module-<module>-collapsible-<group>`, `module-<module>-control-<control>-label`, `-full` and `-promise`, `module-<module>-control-<control>-option-<option>`, a row's own words `module-<module>-control-<control>-as-<words>-label`, `-full` and `-promise`, a preset row's `module-<module>-preset-<preset>-label`, `-full` and `-promise` and `module-<module>-preset-<preset>-option-<option>`, with Custom the shared `preset-custom`, a tool's setting's `module-<module>-setting-<setting>-label`, `-full`, `-promise` and `-option-<option>`, and an action's `module-<module>-action-<action>-label`, `-full` and `-promise`; a unit is `unit-<unit>` from a closed list, and a value with its unit `unit-<unit>-value`, in `ui.ftl` (`docs/gui.md`, Module panels from definitions). Write them in `crates/ui/locales/en-GB/modules.ftl`, and in `uk` and `pl` in the same change (`ui-conventions`).

**The binding is a pure function** of three things: the module's own values, the photo's image context at full resolution, and `base`, exactly each operation's `Operation::defaults(image)` (for a layer, Phase 4 decides its own). It returns the operation parameters it sets, as the crate's `Setting`, which the engine reuses.

- It never reads another module's values, a pipe's scale or region, the clock or any state: the viewport and the export must get the same parameters, and the order controls were used in must not matter.
- It sets nothing for a control at its default. A module at its defaults returns an empty list; that is what makes zero exact. The session holds it to that too: `values` carries only the controls off their defaults for the photo (`ModuleValues::off_defaults`), and a module with none is not bound at all, but a switched module that is on, which is bound with none and whose operation is planned at its own defaults then (decision 32, planned); a switched module that is off is never bound. A control that needs another's value at its default reads it from `self.defaults(image)`.
- It sets only parameters it owns.
- A control that is darktable's parameter itself takes its default from the photo and is bound as it is, with no offset: Exposure is darktable's slider, the control `exposure.exposure` itself, its default the photo's (+0.7 EV on a colour raw, 0 otherwise), over darktable's −18 to +18 EV with its track over −3 to +4 EV. A relative control is written over `base`, so its 0 is the photo as Apertrust first shows it, as darktable writes it: Black level correction is an offset over the photo's own black, within darktable's ±1, the black kept at least 0.01 below the white the photo renders, the margin darktable's `gui_changed` restores, so the kernel never divides by zero (decision 30; `docs/modules/exposure.md`). Where an operation's parameter is not the control's unit, the transfer function inverts the operation's maths rather than adding, states where it has no solution, and clamps there without ever decreasing.

**Transfer functions** are named pure functions in the crate (`transfer.rs`, or the module's file when only it uses one), each with its derivative, which the optimiser needs to fit module values through the kernels' gradients (principle 7). Each has unit tests: monotone where the promise says so, nothing set at the default, both ends of the control's range inside the operation's schema, and the derivative against finite differences.

**Which operations run.** The operations an unedited photo runs have `Manifest::default_enabled` set (decision 22's eight and colour calibration, its untouched state As shot, the camera's illuminant snapped as darktable's `reload_defaults` snaps it, decision 27). Every other operation (colour balance rgb, as in darktable, decision 32; RGB curve, RGB levels, the tone equalizer, vignette, grain) is planned only while some binding sets one of its parameters. So a binding that needs such an operation at its defaults sets one of its parameters to its default value explicitly. Where the operation at its defaults is not an identity (colour balance rgb's gamut mapping; RGB curve and RGB levels in the channel modes turn negative channels to 0; grain at a strength of 0 still moves lightness), the built module keeps it out of the plan while the controls that make it act are at zero (grain while Strength is 0, whatever Coarseness holds), and the first step off zero can change pixels the control does not name: the invariants table measures it. **For a module darktable leaves off, decision 32 replaces this** (planned): the module is switched, its operation planned from the first write of one of its controls until its reset, whatever its values, at darktable's defaults for those not set, so grain at a strength of 0, once on, renders darktable's lookup.

**One instance per module.** A first-pass module drives one instance of each operation it owns, as darktable's module is one instance; RGB curve's channels are its own tabs over one `rgbcurve`. Layers add instances of a module at its slot, run by layer, background first (decision 34).

**Values and marks.** A module's values are its version and, per control, a value (a number, a choice, a boolean or curve points) or none for its default, and a mark: none, kept or Auto. Setting a control keeps it; the marker releases it, keeping the value; keeping an untouched control holds it at its default; a reset removes the value and the mark. Auto and Match move only controls that are not kept, and mark what they set. Marks are saved with the edit (decision 28).

**Session commands** (`docs/engine.md`, Session and threads): `SetControl { module, control, value, done }`, `ResetControl`, `ResetModule`, `Keep { module, control, kept }`, `ApplyPreset { module, preset, option }`, `Reset`, and `CancelGesture { module }`, which puts a module back as it was before a gesture of `done: false` changes, every control's value and mark, follow writes, clamps and a switched module's `enabled`, with no history step (decision 42). The operation-level `Set` (and `apertrust-cli --param`) is only for a parameter no module owns yet, of an operation an unedited photo runs; it is refused for an owned parameter and for any parameter of an optional operation, so no saved value can wait unseen and appear once a module adds the operation. A command's value out of range or of the wrong kind is refused, a number's range the one its module's values give, and so is a choice's option this photo does not list; a saved one is clamped with a warning (decision 30), out of the range its module's values give too, and a saved option this photo does not list is kept. After every change, a number its moved range leaves outside is clamped and kept in the same change (decision 30).

**The edit** is `.apxmp` version 1 (`docs/engine.md`, Edits and Saving): each module touched with its version, the controls set and the marks, and operation parameters only where no module owns them, on operations an unedited photo runs. Version 2 (decision 47, planned) keeps exactly that per module, but inside history steps: each virtual copy of the photo holds a log of steps, a step holding each module it touched with its values after it, or `off` for a reset that turns a switched module off, and the edit a binding sees is each module's values at its last step up to the log's end. So a binding still sees one module's current values and never a step; a module's version and `migrate` apply to each step's entry as they do to version 1's; and a change of a module's stored controls follows the same versioning rules below. The format's text layer is `apertrust-library`'s `sidecar` module (decision 54); the engine keeps the typed reading. No build overwrites an edit a newer Apertrust wrote (decision 48): anything in it a save would drop opens the photo for viewing only. As built, that is a module version above the definition's or a module neither known nor retired; planned, it is also, at the module's own version, a control the definition lacks, an option it lacks, a value for an option or control not ported, or a number out of range (`docs/engine.md`, What a save may drop). So:
- a module that is removed or renamed is listed in `apertrust_modules::RETIRED`, its values then dropped with a warning, as the Tone curve's `tone_curve` will be once it becomes RGB curve;
- a control or an option removed, renamed or narrowed raises the module's version, as Exposure's version 2 will for Contrast and Pivot. While no released edit can hold the old values, its migration may drop them with a warning: the provided `migrate`, whose leftovers the reader drops;
- an addition raises nothing;
- raising a module's version makes the edits it writes view-only in older builds.

A test is to hold each module's stored controls to a committed record (planned, decision 48): ids, kinds, ranges, defaults, options and what is not ported. A removal or change at the recorded version fails until the version rises. An addition fails until the record is blessed with `APERTRUST_BLESS=1`, which refuses a removal at the same version; the review reads the diff.

**Exposure, the first module**, is darktable's exposure page: Exposure, Black level correction and Compensate camera exposure among darktable's other controls, those not ported taking only their defaults. darktable's exposure has no Contrast or Pivot; those are Colour balance RGB's `contrast` and `grey_fulcrum`, with Brightness its `midtones_Y`. Its invariant tests (`crates/modules/tests/exposure.rs`, with the Tone curve's in `tone_curve.rs` and Colour balance RGB's in `colour_balance_rgb.rs`) are the pattern for the next modules, and their shared bench is `crates/modules/tests/common/mod.rs`, which a new module's tests use rather than copy: a bench over a synthetic picture in the working space or a corpus raw, one pipeline updated across plan shapes as the session updates its own, the scene read before AgX and the frame after colorout, ΔE2000 and the sweep from `apertrust-golden`; the corpus's raws and benches are in `tests/corpus/mod.rs`, for the files that run corpus rows. A test file that uses only part of the bench says so where it includes it (`#[expect(dead_code, reason = ...)]` on `mod common;`). Colour balance RGB's table reports its first step, B1, as measured, without a bound, darktable's behaviour; its B4 sets the controls to the golden cases' values and holds the parameters bound, and the kernel's inputs, to the cases'.

## Invariants

Each module's page, `docs/modules/<name>.md`, its English name in kebab-case (`colour-balance-rgb.md`), holds its invariants table, written before the binding (decision 28; `docs/modules/README.md`, Invariants): what each control changes, what stays fixed, what zero means, its range and response, then one row per invariant. A first-pass module's table needs only the rows every table has and the darktable match (decision 22): a control's behaviour is darktable's, which its golden case checks. A table's columns:

| Column | Says |
| --- | --- |
| Row | An id, such as E3, which the test's name carries |
| Control | The control moved, or several for an interaction |
| Moved to | The values tried: the ends, a typical step, the first step off the default |
| Measured | What is read from the render, and where: the scene before the tone mapper, the module's output, the frame (`docs/modules/README.md`, Where rows measure) |
| Must | What holds: renders byte-identical, stays fixed, moves this way, stays monotone |
| Tolerance | How close, in the measure's own unit or ΔE2000, or exact |
| Images | The synthetic ramp or sweep, and which corpus raw |

For example, with illustrative values (the real table is written with the module, and its tolerances are the user's to set):

| Row | Control | Moved to | Measured | Must | Tolerance | Images |
| --- | --- | --- | --- | --- | --- | --- |
| B2 | every control | each end of its range, then reset | the frame | render byte-identical to no edit | exact | ramp, sweep |

The rows every table has (`docs/modules/README.md`, Rows every table has):

- **At the defaults**, the module renders byte-identical to no edit, on every image (exact; the CPU test checks the empty binding too).
- **The first step**, for a module that adds an operation: the operation added at the module's own defaults (the binding's output with each default made explicit, so the operation is planned but changes nothing it is asked to), against the untouched render, on every image: darktable's behaviour, measured and reported without a bound (colour balance rgb's gamut mapping, the tone equalizer's ripple; decision 22). It measures exactly the jump that leaving the operation out at zero would hide.
- **Moved and reset:** a control moved and then reset renders byte-identical to no edit.
- **Order:** the same values set in any order render byte-identical.
- **On a layer** (Phase 4): a control on a full-mask layer at full opacity changes the image as the same value does on the background.

A switched module's table has decision 32's rows in place of the defaults, first step and moved-and-reset rows: off, on at darktable's defaults, the first step on at them, moved then reset, and an older edit, with no row at zero for its controls (Rules, above).

Every row is a test in `crates/modules/tests/<name>.rs`, named as the module's source, which takes the engine and the operations as dev-dependencies, with `apertrust-golden` for its sweep and CIEDE2000 and `apertrust-raw` for the corpus: on the synthetic ramp on CI's software GPUs, and on the corpus raw locally (`#[ignore]`, as the engine's corpus tests are). Unit tests inside `src/` never use the engine: the dev-dependency cycle would compile the crate twice. A control whose table cannot be tested is not yet defined.

## Tone mapping

Tone mappers are modules of their own, as in darktable: AgX now, sigmoid and filmic rgb as they are ported (decision 33), the edit's shown in the Base tab, where darktable's scene-referred workflow lists its tone mapper (decision 38). Exactly one runs, its parameters global, background only (decision 33): a setting chooses the tone mapper for new photos, each edit records its own and keeps it, a photo using another shows that module with a note, and switching an existing photo is an explicit action, one undo step. Every other module acts at its darktable place: those before it shape the scene-referred light it compresses (White balance in the raw stage, Exposure, the Tone equalizer, Colour calibration, Colour balance RGB, RGB curve and RGB levels), and darktable's display-referred effects, grain and vignetting among them, follow it, on layers too (decisions 22 and 33; `docs/engine.md`, Order).

- **Never bind a layer-capable control to a tone-mapper parameter.** A control that must change the tone mapper belongs in the tone mapper's module.
- **A slider means the same on a layer as on the background**: the same binding, to the same operations, over a different `base`.
- **Nothing overlaps.** Every control is one parameter with one owner, so no control sets what another sets.

## Testing a module

- **On the CPU**, in `crates/modules` (the operations as a dev-dependency). `crates/modules/tests/builtin.rs` runs the first four over every module in `MODULES`, so a new module gets them by joining the list:
  - no parameter is owned twice; every parameter a module owns exists (`check::accept`, which the session runs too);
  - every control appears in one row, or only in its lossless views' rows, besides one equalizer's row at most for a number control (`Widget::Equalizer`, the only widget allowed as a second row), and control, coordinate and preset ids are unique together (`Definition::check`, widened with the first view); each view is given and its coordinates' ranges keep its controls in theirs, so neither a set nor a reset is refused (White balance the first to hold to it), its round trip (`unview` of `view` within a few f32 units, and back over the coordinates' ranges) tested with its module, as `testing::Sample`'s is, each preset option's values lie in their controls' ranges and `matching` gives the option back, and every message id the definition implies exists (`messages::of` against `apertrust_ui::i18n::message_ids()`);
  - `bind` at the defaults returns nothing, and a sweep of each control's range, alone and with every control at one end, sets only owned parameters, every value inside its schema (`check::sweep`), on synthetic image contexts; the corpus raws' contexts are still to add. The sweep binds every ported option on every context, whether that context lists it or not, since an edit from another photo may hold any (decision 30);
  - each choice's `options` on every context (decision 30): non-empty, each an option of the definition, each once, in its order, holding the photo's default; every option listed on at least one context; segments only for a control listed alike on every context; and every preset option available on a context writing only options that context lists. The contexts grow to each kind of photo a module lists per photo: a monochrome or four-colour sensor, a DNG with its own matrix, a raw carrying lens corrections;
  - each transfer function: monotone where promised (`transfer::increasing`), its derivative against finite differences (`transfer::check`); its ends inside the schema come from the sweep;
  - its sliders against darktable's, in the module's source: a table of `testing::DarktableSlider`s, darktable's hard and soft ranges in its parameters' units with its factor, offset and digits, and `testing::slider_differences` empty (decision 30), compared through `range` at the module's defaults, and at other values where `range` moves the slider, as AgX's test holds the pivot to darktable's at other input ranges (decision 30). A slider that must differ needs a decision first, and the module's table records it.
  - each number's `range` over the sweep's states (decision 30): finite, `min` below `max`, inside the definition's range, its track inside it, its step above 0; the definition's track and step at the defaults; never moved by its own control's value; the control's default for the photo always inside; one clamp pass enough; no preset option needing a clamp, and no lossless view over a control whose range moves. The sweep still binds every value of the definition's whole range, so the binding stays safe at any value an edit could hold.
- **Invariant tests** for every row of the module's table, as above. A row whose proposed bound fails when measured keeps that bound in an `#[ignore]`d test, named and explained, and CI checks the parts that hold, until the user decides; the bound itself never loosens without a decision (decision 30). The table's Results say which.
- **A control held back:** to keep a built control from users until something it needs lands, take it out of the definition, keeping its binding, transfer functions and rows, as Exposure held back Contrast and its pivot until they left for Colour balance RGB. Taking it out is a removal, so the module's version rises (The edit, above); bringing it back is an addition. Nothing can then set it, since every client is refused a control the definition lacks, and its rows run with `--ignored`, binding it directly. **An option held back,** one its operation ports that an edit may not choose until something lands, is listed in the choice's `unported`, so every client is refused it, while the binding keeps writing it and its rows bind it directly, on CI, as Output colour profile holds back linear Rec709 and linear Rec2020 until the display path converts from the edit's profile (decision 26); letting it in is taking it out of `unported`.
- **Migrations**: an edit saved with the previous module version renders as before.
- **Golden cases** for the operations underneath (`golden-tests`); a binding never changes them.
