# UI conventions

The UI follows the product principles (`docs/principles.md`, decision 1). In the first pass the modules are darktable's, in darktable's words, each with its depth inside it, in its own tabs and collapsible groups (principle 6; `docs/modules/README.md`), and every control keeps to what it says, tested (principle 5; `tool-bindings`). Design around the photographers' jobs in the principles, never by copying a layout for its own sake. It is one egui codebase for the desktop app and, later, the browser.

**Status:** the module panel framework (headers, tabs, sliders) and the design system arrive in Phase 2 (GUI minimum). Their architecture is decided in `docs/gui.md` (decision 36): the design-system crate `apertrust-ui` (tokens, themes, components, the gallery, and translation in its `i18n` module), the actions registry, accessibility and UI tests, with a build order. The tokens and the dark, light and high-contrast themes exist (`crates/ui/themes`, `crates/ui/src/theme.rs`), with the icons (`crates/ui/assets/icons`, SVG) and the gallery; the components come next, in `docs/gui.md`'s build order. The current design of the interface is the UI wireframe on claude.ai (linked from AGENTS.md), which replaces the earlier design canvas; where it differs from this skill or `docs/modules/README.md`, it is newer until its decisions are folded in.

## Rules

- **Widgets only emit commands.** A widget turns input into a command and pushes it to the frame's command list; it never calls the engine or holds engine state (`desktop-architecture`). Its displayed value mirrors the engine's latest state.
- **The Settings dialog is drawn from the settings registry**, the statics each owner's crate generates from the settings schema (decision 43, `docs/gui.md`, Settings and workspace), not written by hand per setting: pages, groups and rows in the schema's order, a row per setting by its kind with the components below, marked and reset by Delete or a double-click when off its default, as a module row, "after a restart" where so, applied at once with no OK or Cancel. Tool settings are drawn in their module, and what the app remembers on its own (the window, the sections open, the scopes' view) is never shown. It has nine pages in a list at its left (decision 43): General, Import, Library, Editing, Processing, Storage, Shortcuts, Presets and AI, a page with nothing yet drawn dimmed and never chosen. General, Library, Editing and Processing (Import later) are drawn from the schema's `page` and `group`; Storage (the user data and cache folders, read-only with how each was chosen; where edits are kept is no setting but each library's choice, decision 47), Shortcuts (the keymap editor), Presets and AI are hand-built panels in the same window and look. A row is darktable's grid: 24 points (`sizes.panel_line`), the label column as wide as the page's widest label in the current language (at least 176 points), then the default dot, then the control; every choice box, number field and text field on a page one width, 180 points, or the page's widest option's up to 220, a number's unit inside its field after the value (`ValueField::suffix`); a checkbox a box at the control's start. Group titles sit on a 28-point line; the page list's names are 15 points, the chosen page on `list_chosen`. A `--conf` row is disabled, "Set by --conf for this run" under it; "Applies after a restart" where the schema says so.
- **Panels are generated from module definitions**, not written by hand per module: the module's controls, ranges, tabs, rows and Auto come from its definition, and each row's actions become module commands (`SetControl`, `ResetControl`, `ResetModule`, `Keep`; decision 28, `docs/gui.md`, Module panels from definitions; `tool-bindings`). The renderer is `crates/app/src/modules.rs`: it returns `Change`s, which the app sends through its pending values so nothing jumps back. A hand-written panel is a gap in the definition format, and so is a renderer branch for one module.
- **Use the design system's components and tokens**, never ad hoc colours, spacing or fonts. Components read the theme from egui's context; a literal colour or size in a component is a missing token. Colours that are data (a hue track, a scope's channels) are the exception. Until the design system exists, keep new UI minimal and note every value that should become a token.
- **Every user-visible string is a message id** (Fluent, through `apertrust-ui`'s `i18n` module): `tr(ctx, "action-undo")`, or `Translator::text_with` with variables. No English literal in labels, buttons, tooltips or errors; `tools/check-ui-strings.sh` enforces it in CI. A new message goes into `crates/ui/locales/en-GB/ui.ftl` and, in the same change, into `uk` and `pl` with the same variables, and into `en-US` only where American English spells it differently (colour, grey, centre, -ise, licence; en-US is an overlay of en-GB, never a copy; `crates/ui/locales/README.md`); counts use Fluent's plural selectors, never sentences assembled in code. Numbers in value fields go through `Translator::format_number` and `parse_number`. Promises, units and module names are messages too. The engine sends error codes; the UI owns the words.
- **Lay out in start and end**, never assume left to right: the side panel already moves sides, and right-to-left languages come once egui supports them.
- **Every component is accessible:** it reports its role, its full name (not the short label) and its value to AccessKit, takes keyboard focus with a visible ring from the theme (drawn through the components' `focus_ring`, which shows it only after keyboard input), and is reachable through the actions registry's shortcuts.
- **Fonts are IBM Plex Sans** (decision 36; `crates/ui/src/fonts.rs`), the only typeface: egui's Proportional and Monospace families are Regular, Medium and SemiBold are named families, and headings and group labels are Medium, SemiBold only where it marks a choice (the chosen tab, a filter's match). egui has no font weight, so emphasis means choosing one of those families. Write negative values with `−` (U+2212), which has the digits' width; the hyphen is narrower and makes a value shift. Never turn egui's `default_fonts` feature back on, and add a font only unmodified and with its licence.
- **Colours are authored in sRGB.** The window is tagged sRGB by `apertrust-display`; once surfaces can be wide-gamut or extended-linear, UI colours are converted for them in one place, never per widget.
- **The principles' quality bar** (`docs/principles.md`): no progress bars while editing; presets and styles preview on hover; everything reachable by keyboard; the interface scales; warnings and overlays stay readable for colour-blind users.
- **A component is built in the gallery first** (`cargo run -p apertrust-ui --example gallery`), in every state, theme and the pseudo-locale, with its interaction test (`egui_kittest`, through AccessKit) and a snapshot, before a panel uses it.

## Module panels

- **Every section is a `Section`** (`crates/ui/src/components`): a module or a utility (Scopes, Layers, History).
  - **Header**: 30 points (`sizes.section_header`), the title (15-point Medium, `text.section_title`) and the buttons centred in it, the whole height the click target and the chevron `text_secondary` while closed, `text` while open or under the pointer. A chevron and the title open and close it; while closed it shows only the title and its buttons, no summary of what is set. A title that would run under the buttons is cut at its end with …, whole in its tooltip and for screen readers, as labels are.
  - **Header buttons**, in the wireframe's order: reset, presets, the last at the header's end; no options button (⋯) on a module, so the title has its room; no Auto button (the wand); no Advanced controls toggle (decision 29). A slider row may also have an Auto of its own, the same wand among the row's buttons before its value, for that one control (not built yet, the `Wand` icon waits for it). A module has reset and presets (`Section::module`); a utility has options only (`Section::options`, which a module ignores). Presets and a utility's options are drawn disabled until something is behind them (`Section::presets`, `Section::options`).
  - **No pin button** and **no on/off switch**. Pinning is set in Customise tabs; holding H over a section, or with its header in focus, shows the photo without it (the section reports `peeking`). The section never reads H: the app's actions registry says whether the peek keys are held (`Section::peek`), so they can be rebound.
  - **A switched module that is off** (decision 32: a module darktable leaves off on a new photo is off until a control changes, then on with darktable's defaults, its reset turning it off) looks as any other: no dimming, no switch, its controls at darktable's defaults as the session reports them. The header's reset is available only while the session reports the module edited (`ModuleState::edited`: a switched module while on, any other while a control is off its default) or a change is pending; the kept marker beside each control set is the other cue. To AccessKit the section is described as "Not applied" (`section-not-applied`) while the session reports it off (`ModuleState::enabled`). Planned.
- **The rhythm of a module panel** (`docs/gui.md`, How the rows are laid out): every one-line row is 24 points (`sizes.panel_line`: the Blended choice, the toggle, the action, a tool setting, a collapsible group's row), the slider row 37; gaps come only from the 2, 4 and 8 steps and each row carries its own: 4 (`spacing.xs`) after the header in a section without tabs, the tab strip 26 points with its first name on the content's 12-point edge, 4 before a collapsible group and 4 after its last row while open. Rows stack with no item spacing.
- **Content tabs** (`Tabs`, drawn by `Section::tabs`): each tab as wide as its name with 8 points at each end, one after another from the row's start, the rest of the row empty, never equal shares; when they do not fit, the padding gives way first, all tabs alike, down to 4 points at each end, and only then the names, in proportion to their widths, darktable's `label / (label + value)` as the dropdown row, each cut at its end with …, whole in its tooltip and for screen readers, on one line, never a second row and never scrolling (`docs/gui.md`, How the rows are laid out). The chosen tab SemiBold in the text colour over a 1-point accent line as wide as its name, the others in secondary text; the accent stays rare (`docs/gui.md`, Themes). In the first pass every darktable tab is a content tab, in darktable's order, masking, masks, options and advanced included (decision 29): RGB curve's and RGB levels' R, G and B while independent, colour balance rgb's Master, 4 ways and Masks, the tone equalizer's Simple, Advanced and Masking, filmic rgb's Scene, Reconstruct, Look, Display and Options, colour calibration's CAT, R, G, B, Colourfulness, Brightness and Grey (decision 27), AgX's Settings and Primaries; darktable's collapsible sections are collapsible groups (`docs/modules/README.md`, rule 5; decision 29). There is no Basic/Advanced split and no Advanced controls toggle (decision 29). Never a second module for depth. Inside a tab, `group_label` groups rows under a small all-caps label so labels stay short.
- **Collapsible groups** (decision 29): each of darktable's collapsible sections is a group in its module, at darktable's place and under its label, closed at first, its open state kept app-wide per group in settings, never in the edit; Reset module leaves it alone. It holds controls, never another group. Its row is darktable's form, not a module header's, 24 points high with 4 above it and 4 after its rows while open: the label in `group_label`'s type (11-point Medium capitals, `text_secondary`), a `divider` hairline to a 10-point chevron at the row's end, pointing to the end when closed and down when open, and while closed a dot after the label when a control in it is set. The whole row is the target, with the hover band and a focus ring after a key; Enter or Space toggles; Tab skips a closed group's rows; to AccessKit a Button with `expanded`, named by its title and described as "N set", its rows the children of a Group while open; search opens the group holding a match. Its title is `module-<module>-collapsible-<group>` (`docs/gui.md`, Module panels from definitions). Draw it with `CollapsibleGroup` (`crates/ui/src/components`): give it the title, whether it is open and how many controls in it are set, and its rows as a closure; it reports a toggle, and the app keeps the open state. The renderer draws a definition's `Row::Group` so, counting the controls its shown rows hold off their defaults, with a tooltip naming that count while it is closed (the wireframe's "Margins: 1 set"), and keeps the open state in settings by module and group (`Shell::group_open`).
- **No Advanced controls toggle** (decision 29): the first pass draws darktable's page as darktable has it, every control in its tab or group. White balance is darktable's white balance page, and Colour calibration's CAT tab darktable's, adaptation first, the closed Area colour mapping group last (decision 27).
- **A preset row** (decision 2), White balance's Settings (decision 27), is a dropdown row whose options each write several of the module's controls through one session command, one history step; its label is the option the session reports the values match, and Custom otherwise. It stores nothing and has no kept marker or reset of its own. Built: the renderer draws `Row::Preset` as a Blended `Choice` (decision 42) with no marker, whose option shows the session's `PresetState::matching`, or Custom (`preset-custom`) through `Choice::none_chosen`, a text the list never offers and the option's place counts; the options the photo cannot have are listed disabled (`Choice::disabled_options`, `preset-option-unavailable`), and a choice reports `Change::ApplyPreset`, which the app sends as `ApplyPreset` and shows once the session reports it, the option's values being the photo's. It is a list: `Definition::check` refuses a segmented preset row until `Segmented` draws a segment disabled. Planned (decision 27): after the row's own options, a heading with the camera's maker and model, darktable's combobox section (not selectable, skipped by the keys and the pointer, to AccessKit the label of the options after it), then the options the session reports the photo lists (`PresetState::listed`); and the row's tuning, a slider row after it drawn only while the session reports it (`PresetState::tuning`), its range, track and step from the report, a whole number, sending `SetControl`, `ResetControl` and `Keep` with the tuning's id, followed at once by the pending display: White balance's camera presets and Finetune, in mired.
- **A view row** (decision 2): a second, lossless view of stored values, such as Colour calibration's Hue and Chroma of its illuminant, or White balance's Temperature and Tint of its coefficients (decision 27). It is drawn as any slider row; editing it moves the stored values, so every other view of them follows at once, from the module's pure view function. It shows the stored controls' mark and reset; a value outside its slider's range shows in its field, the track at its end. Built: the renderer draws a `Row::Slider` naming a coordinate as a `SliderRow` from the session's `CoordinateState` (value, default, mark) and the coordinate's range, step and unit, its words a control's (`module-<module>-control-<coordinate>-…`), laid out as any slider row, with its row's soft range and its coordinate's step as a key's, and disabled only while none of the controls it moves can change the photo, as on a photo open for viewing only; it reports `Change::Set`, `Reset` and `Keep` with the coordinate's id, sent as `SetControl`, `ResetControl` and `Keep`. While a change is pending, `modules::Pending::show` moves the view's controls and coordinates as the session will, through the module's pure `view` and `unview`, the coordinates shown standing in for the session's held ones, so dragging one keeps the others exactly and the controls' own rows follow at once; a change through a control's own row, another view of them or a reset moves the coordinates, so Colour calibration's hue and chroma follow a change of its illuminant, and White balance's temperature and tint a coefficient's.
- **Nothing overlaps** (decision 2). Each control is one darktable parameter, so nothing overlaps and nothing is disabled to resolve a conflict; darktable's presets apply from the header's presets menu, as one change.
- **Background only** modules don't offer themselves on layers; the rest do (the Layers column of `docs/modules/README.md`).

## Controls

- **Sliders**: zero is a no-op on a module every photo runs, and a switched module that is off is a no-op whatever its sliders show (decision 32); ranges are perceptually tuned (UX direction). In the first pass a slider is darktable's: its range darktable's hard range, its track over darktable's soft range (`Slider::soft`), its factor, digits and step darktable's, each module's table audited against darktable's `gui_init` and held to it by a test (`docs/modules/README.md`, Sliders against darktable). Where darktable's range follows other controls, as AgX's pivot spans black to white relative exposure, the row draws the range, track and step the session reports for the module's values (`ControlState::range`, decision 30), never computing them; while a change is pending, `modules::Pending::show` asks the module's pure `range` on the values shown where its answer moves, as it asks `available`, guarded with `catch_unwind`, and shows a value the moved range leaves outside clamped, through the function the edit clamps with, so a drag of black moves the pivot's track and pushes its handle at once.
- **A control the photo cannot use** (`Module::available`, reported with the session's values; decision 30), or that another of the module's controls disables while it holds a value, as darktable makes vignetting's width/height ratio insensitive under automatic ratio (decision 30), is drawn disabled, never hidden; it still takes a value and keeps it. The renderer reads availability from the report and never decides it; while a change is pending, `modules::Pending::show` moves it with the values through the module's own `available`, guarded with `catch_unwind` as `view` and `unview` are, so a control another's value disables is disabled at once (built; `testing::Sample`'s coarseness, unavailable unless its size is coarse and its grain on, is the worked example). A switched module that is off (decision 32) is not drawn disabled or dimmed: its controls take values, and the first one written turns it on (Module panels, above). A control whose parameter is not ported is drawn disabled, as a control the photo cannot use is, and so is a choice's option its operation does not port: every option darktable lists for the photo is listed (decisions 29 and 30). darktable's own settings for a tool, which no edit stores (`docs/modules/README.md`, rule 12: the colour checker's chart), are drawn disabled at darktable's default until the tool comes (`Row::ToolSetting`), and so are darktable's buttons, actions that write controls and are never stored (rule 10: AgX's Auto tune levels, Read exposure, Reset primaries and Set from above), each an `ActionRow` (`crates/ui/src/components`): one line, egui's button, themed, at the start, its promise the tooltip and its full name to AccessKit (`Row::Action`). A collapsible group with no rows yet, AgX's Show curve until a read-only graph row exists, is drawn disabled and closed with the tooltip a titled tab with no rows has (`CollapsibleGroup::disabled`, `section-tab-later`).
- **A row darktable shows only for one mode,** or while another control holds a value, follows it, hidden otherwise, as darktable does (decision 29); that is the one case of a row not drawn, and it is not a disabled state.
- **A choice lists the options darktable lists for the photo** (decision 30; built, `testing::Sample`'s method, camera only on a photo that records a bias, the worked example): the session's `ControlState::options`, in the definition's order (demosaic's sensor's methods, as shot in camera only on a colour raw).
  - Options the photo does not list are not drawn and not announced. That hides no value, because one the edit holds is always shown: last in the list, chosen and drawn disabled, "Not available for this photo" (`choice-option-unavailable`), and in the box's tooltip.
  - That option leaves the list once another is chosen, as darktable's combobox re-adds a stored value at its end.
  - To AccessKit the box's value is that option's name, its description "Not available for this photo".
  - Unported options among the photo's are drawn disabled as before. A choice whose options vary between photos is a list, never segments.
  - The renderer takes the list from the report and never decides it.
- **A value is what its row shows:** a dragged or typed value is rounded to the row's decimals, as darktable rounds one to its digits, and the renderer rounds every value to them before it sends it, so no value it sends reads as untouched while it is not. The step is what a key moves, never a drag's grid: darktable's step at rest, growing with a widened track's span as darktable's zoom step makes it, and a key's move, Alt's tenth included, never less than the last decimal shown, darktable's `min_visible`.
- **Units and signs** (decision 42): `SliderRow::unit` names the message that writes a value with its unit (`unit-ev-value`), which the row now draws at rest and screen readers hear; the field shows the number alone. A slider signs its values while its range spans zero, `min < 0 < max`, zero as "+0.00", darktable's rule, which `SliderRow` applies from its range (no `signed` to pass). Ukrainian writes darktable's "50%" and "px".
- **Dragging is the fast path**: a drag sends a command per change, and the engine renders the latest state (`desktop-architecture`); never debounce in the widget.
- **Use the slider row, `SliderRow`** (`crates/ui/src/components`), in two lines and compact, darktable's sliders the example of density (`docs/gui.md`, How the rows are laid out): 37 points, the label and marker at the start, the row's buttons (Auto, the picker) just before the value at the end, all a field high (`sizes.field`, 18), and the track the content's full width below in a 16-point strip. Never build a slider from egui's own. Rows carry their own padding, so a section stacks them with no item spacing. Room for density comes from the value, the gaps and the strip, never from the handle, which never shrinks and sits on the track as the wireframe draws it, its tip and base 5.5 points each way of the track's middle, inside the strip. `sizes.control` (22) stays for the bars, the headers, segmented controls and egui's own widgets; a module row's parts use `sizes.field`.
  - **The value** (decision 42, `docs/gui.md`, Slider values and choices): at rest read-only text with its unit, as darktable writes it, in the small text (12), right-aligned 5 points from the row's end, no box, never cut, the label cut instead; the `hover` band and an I-beam under the pointer; a click on it never moves the slider. A click on it, or a digit, a minus sign or the decimal separator typed on the focused slider, makes it the value field (54 by 18, wider only when the number needs it; right-aligned 5 points from its end, typing included), holding the number alone with no `+`, selected. It takes a number only, for now (`ValueField::number_only`): digits, a leading minus (`-` or U+2212) and one decimal separator, the point or the language's own; any other character is ignored as it is typed or composed, a second separator or a minus past the start is refused, and a paste, or a screen reader's set value, is taken whole or refused whole, never filtered, which would change a pasted number's size ("1e-5" to 15), so the field never holds text that is no number. Screen readers hear its unit in its name, "Exposure, in EV" (`field-value-in`), since it holds the number alone. darktable's expressions through `apertrust_ui::calculator`, built, wait until there is a need, and with them the trailing unit dropped and the `error` border. Enter, Tab or a click elsewhere sets it, clamped to the range, Esc puts it back, an unchanged value sets nothing, and a field left empty or with a sign or a separator alone puts the value back, with no error; after Enter or Esc the focus is the slider's again. Key names follow the platform, as the actions spell them: Return on the Mac, Enter elsewhere. Plain `ValueField`s (Export's sizes, the memory budget) keep `parse_number`. Nothing in the field turns the accent while a value is edited, dragged or typed: the text colour, `field_selection` behind a selection, the cursor in the text colour. Never cut a value's decimals.
  - Double-click on the label or the track, or Delete, resets to the default; a double-click on the value selects its number. Arrow keys step (Shift ten steps, Alt a tenth), Home and End go to the track's ends, and a digit, a minus sign or the decimal separator opens the value field starting with it, so digits rate the photo only when no slider or text field has focus (`docs/gui.md`, The caption under the photo). Enter opens darktable's popup, as darktable's own key does, and so do a right-click on the row but its buttons, a Control-click on the Mac, Shift+F10, the Menu key and AccessKit's ShowContextMenu (decision 42); until the popup is built, Enter opens the field.
  - **The slider popup** (decision 42, `docs/gui.md`, The slider popup): darktable's fine control, a kind of the popup service drawn on every platform, never an `Area` of the row's own. It sends `SliderAction::Set { done: false }` while the photo follows and `done: true` as it closes keeping the value; a cancel (Esc, leaving it, a press outside, a right-click inside, an app key) reports `SliderAction::Cancel`, which the renderer sends as `CancelGesture { module }`, and the session puts the module back exactly, with no history step. Never put a cancelled value back with `SetControl`: it would leave follow writes, clamps and a switched module on.
  - A drag reports every change and once more, marked done, on release, so history merges it into one step.
  - **A soft range** (`SliderRow::soft_range`), as darktable's: the track spans it at rest, and the control's range stays what a value may hold. A value beyond it, typed, pasted, or set by a script, a preset or an edit, reaches the range, and the track widens just enough to show it, keeping that span until the row is reset; a drag, a click and the keys stay inside the span shown, Home and End at its ends. Screen readers are told the control's range as the limits, and step inside the span (`docs/gui.md`, How the rows are laid out). A soft range the session reports moved starts the span again from it, widened just enough to show the value, as darktable's `dt_bauhaus_slider_set_soft_min` resets its visible range (decision 30).
  - The fill runs from the default; `no_fill` for values with no direction, such as a hue. Colour tracks (temperature, tint, hue) are data colours.
  - The marker shows ● when kept, ○ under the pointer or focus, and "A" with the old value's tick while a Match proposal waits.
- **Popups go through the popup service** (decision 40, `docs/gui.md`, Popups): a dropdown, a pull-down or a context menu is a request of plain items, native on the Mac and drawn elsewhere, never a popup a component draws for itself. Built so far: the drawn pull-down (`apertrust_ui::popup`, decision 40): open a `Request` with `popup::open` under an id of your own, read `popup::answer` on the frame it arrives, once; the app calls `popup::show` once a frame, and a popup not drawn for a pass closes. Each level is an egui `Area`, and while one is open an egui plugin gives it the plain keys and typed text before anything else reads them, F-keys and keys with Ctrl, Cmd or Alt staying the app's; never draw a drawn popup with egui's `Popup` or menus, which own no keys and have no type-ahead. A submenu opens after the pointer rests 0.2 s on its line (`PAUSE`, a constant, not a motion token: it reads intent); a press outside closes every level without giving the focus back or swallowing the press. ⋯, » and ⋮ go through it too (`components::pull_down`): no popup in the app uses egui's `Popup`, and a menu holds items only, a setting being an item with a check mark, never a checkbox; `Choice`'s list is the service's dropdown kind (`Request::dropdown`, built; `Choice` opens it itself and calls `popup::show`, so a window that draws one needs no call of its own), with darktable's type-to-filter wherever it is drawn (matches anywhere, case-insensitive, the matched characters in SemiBold and the other options at half strength; a key matching nothing dropped; Backspace taking one back; Enter taking the only match that can be chosen, and with nothing typed the highlighted option). On the Mac every plain list, a choice's included, is AppKit's menu through the service the app installs (built: `popup::Service`, decision 40), with AppKit's type-to-jump in place of the filter; so a component never assumes its popup is drawn: it reads only `popup::answer`, `is_open` and `anchor`, and names itself as the request's opener (`Request::opened_by`) so the focus comes back to it after a press opened the popup. The slider popup is a kind of its own, taking Alt with the arrows and Paste too, any other key with a modifier or an F-key cancelling it before it runs (decision 42). Whatever previews on hover (presets, styles) or holds controls, colour or thumbnails is drawn on every platform, from the tokens.
- **A dialog is a native modal window, a confirmation the system's alert** (decision 41; `docs/gui.md`, Dialogs and alerts).
  - Settings, Export, Customise tabs and every prompt for a name each open in a window of their own through the app's dialog host, modal to the window they rise from but Settings, which is modeless (built on every platform as a `Dialog` of the host, `docs/gui.md`, How a dialog is built now). Their content is drawn with the design system's components in a function of `&mut Ui`, with no `egui::Modal` and no `scrim`.
  - About, as built, and a future splash screen are the only exceptions, Apertrust's own modals over the window, and the `scrim` token is theirs alone.
  - A dialog opens with the focus in it and gives it back to its opener; Escape cancels and Enter presses its default button. Settings on the Mac is Apple's Settings window instead: no Close button, Escape does nothing, Cmd+W closes it, and it opens where it was last left.
  - Its buttons sit at the end of its last row in the platform's order, on the Mac the default button last, drawn with `dialog_host::buttons`, which lays them out from the row's start so screen readers and Tab meet them as they are seen; never egui's right-to-left layout for them.
  - A confirmation is a request to the alert service (title, message, buttons with words and roles), never a drawn yes-or-no in a dialog: `NSAlert` on the Mac, the task dialog on Windows, Apertrust's own alert on Linux. Its words are Fluent messages, never the system's OK and Cancel.
  - Print and Import stay full-window sheets in the main window until the user answers whether they are dialogs.
  - **The Export dialog** (`crates/app/src/export.rs`; `docs/gui.md`, The Export dialog) is darktable's export module row for row in sentence case: its choices are `Choice` in the Boxed style (decision 42's C14, never Blended outside module panels), a row not built is drawn disabled with the reason in its tooltip rather than left out, the path is a `PathField` (a variable list that is part of the row, never a popup, so the field keeps the focus), and what the session says under a row (names, files already there, the size, a problem that stops Export) is a small note in `text_secondary`, `warning` for a replace and `error` for what stops Export, with the reason in the disabled button's tooltip. Its keys are the dialog's own: Esc closes the innermost thing first, Return exports only when no control has the focus, Cmd+Return anywhere, F6 between its three regions.
- **The other controls** are `IconButton`, `Segmented`, `Choice`, `Swatches` and `ValueField`. A choice is a dropdown row, always one line, 24 points high in a module panel (Blended, `sizes.panel_line`) and 20 in a Boxed row, in one of two styles (decision 42, `Choice::style`): **Blended** in module panels only (module choice rows, preset rows, tool settings' choices), darktable's combobox, the label at the start, the kept marker after it as a slider row's on a control's row (`Choice::mark`: ● while kept, ○ under the pointer or focus, a click reporting `ChoiceAction::ToggleKeep`, sent as `Keep`), none on a preset row or a tool's setting, the row's buttons, then the option right-aligned in the small text with a 10-point chevron whose stroke ends where slider values end, no box, the hover band across the row and the focus ring round it; **Boxed**, the default, everywhere else (Settings, the other panels, Export, Customise tabs), the box (18 high) at the end on the value fields' edge, as wide as its widest option, with no hover band (the box alone is the control) and the focus ring round the box. The whole row opens it but its buttons; when they do not fit, the label and the option or box share the line in proportion to their widths, as darktable's combo boxes do, each cut at its end with … and whole in the tooltip and for screen readers. `apertrust_ui::components::ChoiceStyle` is not the definitions' `apertrust_modules::ChoiceStyle` (a list or segments): name the design system's by its path in the renderer. A `Segmented` in a module is two lines: its label above, the buttons across the full width below. A boolean in a module is a `ToggleRow`: the checkbox at the start, outlined in `control_outline` (3:1 on `panel` and `sunken`, `text_secondary` under the pointer) so an unticked one can be seen, its label after it. One of darktable's buttons is an `ActionRow`: egui's button, themed, at the start. The dropdown, checkbox and action rows are one line. Checkboxes and text buttons are egui's own, themed; menus go through the popup service, above. An `IconButton` toggle that is on shows its filled icon (`Icon::filled`) in the text colour with no box; one whose icon has no filled form (a quad's picker, the ☰ with its menu open) is drawn pressed, a raised fill with a hairline.
- **Use the curve, `Curve`,** for any curve of points (`docs/gui.md`, The curve). Give it the points and the curve to draw (samples or a function; the widget knows no spline), and its handles as `levels` (input levels; the first and last points stay) or `ends` (the curve's own ends; every point can go, and points and handles keep their order). It reports one `CurveAction` a frame and never one the module would refuse: points out of order or closer than 0.0025, more than `max_points`. A drag reports every change and once more, marked done, on release.
  - Pressing adds a point (on the curve when the press is near it) and drags it at once; a double-click removes one. Page Up and Page Down choose points, the arrows move them by its step (Shift ten, Alt a tenth), Insert or + adds one midway, Delete removes it and Shift+Delete resets. Only moves repeat while a key is held. Keys with Ctrl are the app's, and each handle is a slider of its own after the plot.
  - `enabled(false)` dims it and ignores input. A point's accessible name carries its input and output, since VoiceOver reads only a list item's name.
- **Use the equalizer, `Equalizer`,** for the tone equalizer's graph of its bands, the registry's `Widget::Equalizer` (`docs/gui.md`, The equalizer). Give it the bands, each node's name, the curve sampled over their exposures, whether no curve fits them, the curve's smoothing σ, where a drag's bands settle after each step (`settle`, from the module's curve), and the mask's histogram as `MaskHistogram` (the bins, their range in EV, the 5th and 95th percentiles), or `None`, which draws no histogram and no warning. It reports one `EqualizerAction` a frame: `Move { from, to, done }`, `ResetBand` and `Reset`.
  - A drag anywhere moves the bands around the pointer as darktable's does, every change and once more, done, on release or as the pointer leaves the graph; a double-click resets every band. Page Up and Page Down choose a band, the arrows move it by its step, never less than the last decimal shown (`decimals`), Delete resets it and Shift+Delete every band; keys with Ctrl are the app's.
  - Each band is a slider for screen readers, named by its band; the graph's description says where the mask overflows the bands, which darktable's warning sign says without words. The histogram is `graph_histogram`, a token of its own.
- **Use the scopes, `Histogram`,** for the histogram, the waveform, the RGB parade and the vectorscope (`docs/gui.md`, The scopes). Give it the app's `ScopeView` and the engine's counts as small arrays (`HistogramBins`, `WaveformBins`, `VectorscopeBins`) with the shares that clip (`Clipped`); it knows nothing of the engine. The engine measures only the graph shown, so a graph with no data yet can still be chosen and says "Nothing measured yet"; only a graph the app cannot measure (`available`) is disabled, and a channel only once the graph's data lacks it. The clipping toggles stay disabled until the app draws the overlays (`overlays(true)`). It reports one `HistogramAction` a frame, which `ScopeView::apply` applies; the overlays on the photo are the app's.
  - Its controls show only while the pointer is over it or one has focus, and stay in the focus order and for screen readers while hidden. The graph is an image described by what clips;
  - The channels' colours are data, alike but for their order, so the three read grey together whether they mix as light, on a dark ground, or as ink, on a light one. Luminance takes the text colour and the clipping marks the theme's clipping colours.
  - Its open choices are listed in `docs/gui.md`.
- **Other custom widgets** (colour wheels, the tone equalizer's band curve) are drawn with egui's painter, follow the same command rule and, like the curve, take only the keys the app leaves a focused control: none with Ctrl. A widget that draws what the engine measured behind its controls, the tone equalizer's band graph over its mask histogram or RGB levels' handles over their input histogram, takes it as plain arrays the app hands it from the session's readout (decision 19; `docs/gui.md`, Module panels from definitions), says nothing measured while it has none, and asks the engine for nothing; darktable's drawing of it (its height, its warnings) is the widget's, from those arrays.

## Layout

- **One view** (decision 37): no separate views. The side panel's tabs, Library among them, stay the same whatever the central panel shows, and a key means the same everywhere. The central panel shows a layout, Photo (the active photo, or the selected photos side by side, up to 11 and a 12th cell saying how many more) or Map (later), switched only when the user asks: by the central bar's Map toggle after Guides, its key Shift+M, or a command that names it, as "Show on map" does; pressed again, the toggle goes back to Photo. There is no Grid layout: the grid panel shows in every layout, and Phase 3's culling is Photo with the grid panel and the caption's ratings. Opening a tab or using a section never changes the central panel. With no photo the central panel says "No photo selected". Sliders and Reset act on the active photo, outlined in the accent; the rating keys, Apply edit and Export on every selected photo, showing how many, with one Undo; there is no "edit all selected" toggle. In words the user sees: Folder, Album, Smart album, Group; never "collection". A workspace is a named, saved set of the side panel's tabs, never the model. `docs/gui.md` holds the details as the UX designer redraws them.
- **The top panel** (`TopPanel`; `docs/gui.md`, The top panel): on the start side the mark (the Folded A in one colour, `crates/app/assets/icons/svg/apertrust-mark-mono.svg` tinted `text_secondary`, never the colour mark; drawn plain in a 30-point square, with no hover and no tooltip, a click opening About; to AccessKit a button named About Apertrust that a key can focus and press, so not part of the area that moves the window), and on Windows and Linux the ☰ before it (decision 39); no switcher (the central bar's Map toggle, after Guides, switches the central panel between Photo and the map); then the common actions, Copy edit and Apply edit a group of their own. On the end side: the activity, an assistant's connection and Saved. The jobs are `Jobs` (`TopPanel::jobs`; built, decisions 56 and 57): one spinner beside Saved, an icon button, never one per job, drawn while any job is queued or running (it turns, and holds still where the theme's motion is zero) and, with only ended jobs left, as the tick or the warning sign; it has no words, so it never folds and a save never moves it; named "Jobs" with the count in its value ("2 running"), so its name stays while jobs come and go, in the Tab order, reported as `TopPanelAction::Jobs`, with a polite live region that speaks at a job's start and end only. `Jobs::window` draws the jobs window's content into any `Ui` (the app hosts it in a window of the dialog host): a row per `Job`, newest first, as a group named by its translated `JobMessage` (`job-…`, arguments as plain `JobArg`s), a bar, its details and its buttons; an export's `ExportDetails` bring "3 of 12 done · now IMG_2044.ARW", the folder, a failure's reason in `error`, and the buttons Show in Finder, Cancel export, Try again and Dismiss; a queued job says so, and a job that cannot be cancelled has no Cancel. It takes plain data and returns `ActivityAction`s. Every row's buttons are ordinary buttons in the Tab order. Groups are told apart by `spacing.xl`, never a line. No Settings button. It folds by measuring its parts at the current scale and language, never at a fixed width, in the order `docs/gui.md` gives, the actions' words first.
- **The top panel is the window's title bar** on every platform (decision 39, `docs/gui.md`, The window frame and menus): it runs to the window's top edge, starts after the Mac's traffic lights by the inset the platform reports, and on Windows and Linux holds one menu button, ☰, at its very start, before the mark, which opens the menus as submenus of one drawn menu and never folds (decision 39: no menu titles; F10 opens it, and Alt with a top-level menu's access key opens it with that menu expanded, so Alt with a letter stays kept from shortcuts), and the caption buttons (minimise, maximise or restore, close) at its end, AccessKit buttons drawn from tokens. The window can be as narrow as 500 points (decision 39), so every part of the shell must give way below 960 rather than clip; how the side panel does is an open design item (`docs/gui.md`, Open questions). Its empty areas move the window and maximise it on a double-click, so nothing interactive is drawn there without being reported as taken. Built on the Mac: `TopPanel::title_bar` and `start_inset`, reporting `MoveWindow` once a drag from an empty area has moved and `TitleBarDoubleClick` (and, for Windows and Linux, `WindowMenu` on a right-click there, and the caption buttons through `caption_buttons` and `maximised`, used by the app on Linux). Built on Linux: the ☰ through `TopPanel::menu_button`, reporting `TopPanelAction::Menu` on a press or ↓, drawn pressed while its menu, the popup `TopPanel::menu_popup`, hangs from `TopPanel::menu_anchor`, a press then closing it; F10 opens or closes it (the `menu` action, Linux only until Windows' ☰), Alt with a top-level menu's access key opens it at that menu (`actions::access_key`), and the menu closes when a key runs an action or a dialog opens. Windows' ☰ is not built; a control drawn in `TopPanel::show` goes through its `pressed`, which takes its rectangle, with egui's margin round it, out of the empty areas, disabled or not. The empty areas are read from the pointer, never from a widget under the panel, which would take that margin from the controls.
- **An action that can't run now is drawn disabled** (`Available`, `Toggle::enabled`, `TabBar::customise`), never hidden, and never left live with nothing behind it.
- **The side panel** (`TabBar`, `PanelBody`, `PanelEdge`): icon tabs with names (Library, Base, Colour, Correct, Effect, History in the Edit workspace: darktable's scene-referred groups under darktable's labels in British English, with darktable's icons in one colour, between Apertrust's own Library and History, opening on Base; no quick access panel or active-modules tab; decision 38), which shrink together by up to two points when one is too long for its tile and then end in an ellipsis, the full name in the tooltip; » for the tabs that don't fit and ⋮ for the tab options; then each tab's pinned sections (Scopes and Layers by default), a 4-point band, and the rest scrolling with a scroll bar that is always there and quiet: its own tokens (`scroll_thumb`, `_hover`, `_active`) on a `sunken` track, never a bright one. A tab with nothing behind it yet, History until built, is drawn disabled, saying it is to come, never chosen and its keys unavailable (`PanelTab::enabled`; the app's `TABS_ENABLED`). In each group's tab the modules sit as darktable's right panel lists them, in pipeline order with the last module at the top, each in darktable's group, and a module darktable puts in no group in the group darktable's other layouts give it (decision 38; `docs/modules/README.md` keeps the lists, the app's `TAB_MODULES` holds them, and a test holds each to `OPERATIONS` reversed). Tabs are a user workspace: sections can move between tabs, appear in several, or sit in one, and every module sits in at least one. The panel can sit on the right or the left. Its width is the user's: dragged at its edge towards the photo (`PanelEdge`, the separator itself, `border` under the pointer, with the column-resize cursor), or with the edge focused by Tab, ← and → (10 points, 50 with Shift), Home and End, from 240 to 600 points, 320 at first, never more than half the window but never under 240; a double-click or Delete goes back to the theme's. Everything in it must work at 240, its narrowest (`docs/gui.md`, The side panel).
- **The central bar** (`CentralBar`) over the photo in the Photo layout: its toggles (the selected photos, Proof margin, Before and after, Guides), the layer menu, the values under the cursor (only when they fit between the two ends) and the scale: Fit, − a logarithmic slider +, with stops from 50 to 1600%. The photo and its caption are one block in the central panel's slot, laid out by `PhotoFrame` (the margin, Proof margin's larger margin with no white, the room the engine renders the photo for) and the caption drawn by `PhotoCaption` (`components/photo_frame.rs`; `docs/gui.md`, The photo frame). Guides over the photo, the composition overlay (decision 37), use the `guides` token, translucent and the same in every theme. The surround behind the photo is one of six neutral greys, Black to White (`apertrust_ui::Background`, `Theme::with_background`), chosen from a right-click on the surround (never on the photo, which keeps its right-click for a menu of its own) or View › Background, the theme's own `photo_surround` until one is chosen; the caption's text is `Colors::text_on_surround`, whichever of `surround_text` and `surround_text_on_light` reads better (`docs/gui.md`, The background).
- The viewport in the central panel, drawn by a paint callback, one texel per physical pixel at fit-to-window, the last frame scaled only while the window resizes (`desktop-architecture`, decision 18).
- **The grid panel** (`GridPanel`, of `GridCell`s) runs under the central panel, not under the side panel, shows the current folder or album and draws only the visible cells. A click makes a photo active, Shift-click selects a range, Ctrl or Cmd-click adds or removes one; with a cell focused the arrows, Home and End move between cells and Enter opens one. **`GridCell`** is a square of the grid bar's Zoom size (Small 84, Medium, Large 176, Extra large 256) with darktable's thumbnail marks in darktable's places (the UI wireframe): the picture at the square's bottom centre, or filling it with `grid_panel.square_thumbnails`; under it, while the grid bar's Labels shows them, a caption: from Medium up a first line of the reject mark, five stars and the colour labels as one circle (split into segments for several, its click opening their list), drawn unrated until the library keeps ratings, then the file name; at Small the name alone; on hover or focus, on `thumb_scrim` with `text_on_thumb_scrim`, the file type and the edited pencil; a lock or a warning always; the outline `border`, a thin `frame_ring` for selected, a thicker for the active photo, never the accent; a list item named by the file with its marks in its description. It takes plain data (a name, flags), no library types. A thumbnail is the camera's embedded picture first, shown unmarked as darktable shows it, then Apertrust's own render of the photo, a still of the viewport pipe, the file name in its slot while neither has come or where the raw holds none (`docs/library.md`, Thumbnails).
