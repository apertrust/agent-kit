# Desktop architecture

The rules here come from `docs/decisions/` and `docs/architecture.md` (decisions 5, 8, 17, 18, 35, 37, 41, 43 and 56 above all) and from what the Phase 0 viewport spike taught. They exist to keep the UI responsive while a 60 MP image is edited, and to keep the engine usable by every client: the desktop app, the CLI, the web client and MCP. Cheap to follow now, expensive to retrofit later.

The app in `crates/app` is the shell (`docs/gui.md`) with one raw in the central panel, rendered by the engine's session on its own thread through the viewport pipe (`pipeline::Pipe::Viewport`, decision 12) and drawn by a paint callback (decision 17).

The app is one view (decision 37): no separate views. The side panel's tabs, Library among them, and what a key or a button acts on stay the same whatever the central panel shows. The central panel shows a layout, Photo or Map (later), which is interface state and changes only when the user asks: the central bar's Map toggle after Guides, its key Shift+M or a command that names it ("Show on map"), never a tab or a section opening. There is no Grid layout; the grid panel shows in every layout. Sliders and Reset act on the active photo; the rating keys, Apply edit and Export on every selected photo, saying how many, one Undo for all. The code's `View` and `Scope::View` are to become layouts and a layout's scope. A workspace is a named, saved set of the side panel's tabs, never the model.

- **Dependencies point towards the engine, never away from it.** The engine never depends on egui, eframe, winit or any client crate; a type the engine needs from a client is a sign the boundary is in the wrong place.
- **A crate is added when its first real code lands**, not before, in `crates/<name>`, its package name without `apertrust-` (operations in `crates/op/<id>`, decision 65), and listed by name in the workspace's `members`, with shared versions in the root `Cargo.toml` (AGENTS.md).
- **Data files live in the top-level `data/`, as darktable's** (decision 45): darktable's data files verbatim under darktable's names, and those several crates or readers outside Rust read, the settings schema first. A file comes with its first consumer, never before, with its entry in `data/README.md` (provenance, licence and readers; for darktable's the tag, the blob, the size and the SHA-256) and, for darktable's, a test in the embedding crate holding the SHA-256. It is embedded at build time, with `include_str!` or by a build script, by the one crate that parses it; other crates reach what it parsed through that crate or the image context, never with an `include_str!` of their own: `apertrust-raw` parses `wb_presets.json` and carries the camera's presets in the image context (decision 27). Nothing reads data from an installed folder at run time. The workspace publishes no crate, so an `include_str!` may reach outside its crate's folder. Themes, icons, fonts and locales stay in `apertrust-ui` (decision 36), kernels in their operation crates (decision 20), tests' fixtures with their tests.
- **`apertrust-base` holds only what every program sets up as it starts** (decision 43): logging and the banner, the version, folders and settings. Nothing about images, colour, the GPU or the UI goes into it, so it never becomes a grab bag as darktable's `src/common/` did; helpers that ports share follow decision 65. A crate that needs one part turns on that part alone: `apertrust-ui` the settings part, for `Choice`; the golden harness, which reads no settings, the log. These stay crates of their own, each for its reason: `apertrust-display` and `apertrust-fs` (FFI, allowed `unsafe`), `apertrust-raw` (rawler), `apertrust-color` (the kernels' Slang import path), `apertrust-plugin`, `apertrust-operations` and `apertrust-modules` (layer boundaries), `apertrust-ui` (egui).
- **No C or C++ compiled in or shipped** unless no Rust option exists (decision 5); ONNX Runtime is the exception. Libraries the platform provides and Apertrust never ships, loaded at run time, are outside the rule (decision 5): the Vulkan loader and drivers (wgpu), libwayland, libxkbcommon and the X11 libraries (winit), libdbus (rfd), and the OS's own frameworks and system DLLs (Metal and AppKit, Direct3D 12 and FXC's `d3dcompiler_47.dll`). A crate whose build script compiles C (`cc`, `cmake`), or a library Apertrust would bundle or download, needs its own exception: stop and ask. Prefer a crate's backend that compiles no C and, on Linux, loads a platform library at run time rather than linking it when built, so a desktop without it loses that feature instead of the app failing to start: rfd's `xdg-portal` rather than its GTK backend, for example.
- **Few crates** (decision 65): new code goes into a module of an existing crate, base's behind a feature or the library's; a crate of its own only for `unsafe` FFI, a dependency direction that would otherwise break, or a decided boundary (an operation's). Say the reason in the brief.
- **`unsafe` only in FFI crates**, with `#![allow(unsafe_code, reason = ...)]` at the crate root. Platform code that needs Objective-C or Win32 calls goes into `apertrust-display` or a sibling FFI crate, never into the app; the file system's (bulk listing, cloud flags, safe writes) into `apertrust-fs` (decision 53).
- **The library's files are the truth** (decisions 46, 47 and 52 to 55; `docs/architecture.md`, Library and sidecars). Sidecars and a library's small TOML files hold everything shared; a database is never the truth and never sits in the library's folder, on a share or in a sync folder; a library's cache is per machine and rebuilt from the files. Nothing is written into the person's folders but sidecars, a library's files and a root's id file, once: no lock files, caches or hidden indexes. Every file is written whole, through a hidden temporary flushed and renamed, only when its bytes change, and read again first if it changed since this machine read it. Folders are listed in bulk through `apertrust-fs`, never with a metadata call per file (21.6 s against 0.3 s for 2,825 files over SMB on the M4), and sidecars read 16 at a time; each root's calls run on the library's threads with deadlines, so neither the interface nor the engine ever waits for a share; a cloud placeholder is never read in the background. Shared files name a photo by its root's id and an NFC path relative to the root, never an absolute path. The library's layers call only the layer below (decision 54): no SQL, no trait with one implementation, no second API beside the session protocol.

## The engine–UI boundary

Every client reaches the engine the same way, so undo, agents and the remote web mode behave identically (architecture: Engine architecture).

- **Widgets only emit commands.** A widget turns user input into a command value and pushes it to the frame's command list; it never calls engine methods or holds engine state. The app loop forwards the list to the engine.
- **The session protocol is the boundary** (`docs/session-protocol.md`). Until `apertrust-protocol` exists, `apertrust_engine::session`'s `Command` and `Event` stand in for it. Shape new commands so they will move into the protocol unchanged: plain data, no references, no GPU objects.
- **Clients speak modules, not operations** (decisions 4 and 28). A widget sends `SetControl { module, control, value, done }`, `ResetControl`, `ResetModule` or `Keep`, with the module's and the control's ids, and a slider popup's cancel `CancelGesture { module }`, with which the session puts the module back as it was before the gesture's first `done: false` change, follow writes, clamps and a switched module's state included, with no history step (decision 42); the session's bindings turn them into operation parameters. What a field or the popup reads as typed, a number only for now and darktable's expressions through `apertrust_ui::calculator` once there is a need, is turned into a number by the client: the session gets numbers. The operation-level `Set` is only for parameters no module owns yet, of operations an unedited photo runs; the session refuses it for any other. No client translates module values itself, so the CLI and MCP see what the app sees.
- **The session saves the edit on a writer thread** (decision 28): the engine thread hands it the latest edit after each completed change and when a photo closes, so a slow disk or a network share never delays a frame; a failed write comes back as `Failed`, the edit kept in memory.
- **The engine answers with events**: a new frame is ready, a render failed, an image loaded with this metadata. The UI renders from the latest event's data. Every event follows decision 59 (`docs/events.md`):
  - **State its kind** in `Event::topic()`, `Topic::Fact(Fact)` or `Topic::Notice`, and in the tests' own matches (`session.rs`'s exhaustive one, and `kind` in `session/outbox.rs`): a fact, the whole current state of one topic that supersedes the last (values, a frame, a reading, a job's progress, the selection, a page), or a notice, something that happened once (opened, saved, failed, a job's end, a listing's chunk, a delta). A fact carries its whole topic; never send half of one.
  - **Number it**: `through` where it includes commands, the open's number where it is about what a command opened, `command` where it answers one; a refused command is `SessionError::Refused { command, error }`.
  - **Send it through the session's `Outbox`** (`crates/engine/src/session/outbox.rs`; `send`, or `send_all` for a batch, one wake for the burst), never a channel and a `wake` of your own; a thread or job body that reports gets a clone of it, as the export job's `Run::outbox`; a lower crate (base's jobs, the library) takes an observer closure and knows nothing of `Event`. A send never blocks, and no producer waits for a client: a question to the user is a notice and an answering command, waited through `Context::wait`.
  - **One event per command or batch**, never per item; progress at most every 0.5 s; carry what a client shows, so it never asks again for each item, except a collection's photos, read by page after `CollectionChanged`.
  - **Order** only within one producer, and within a batch a refusal before the values and the values before the frame; across threads compare numbers, never arrival.
- **In the app, events enter in one place**: the mirror's `apply(event) -> Vec<Reaction>` (`crates/app/src/mirror.rs`, decision 59), drained in `App::logic`, free of egui and tested by feeding it events. No event bus and no subscriptions: panels draw from the mirror each frame; a derived cache compares the mirror's generation; a one-shot reply (a window opening, a preview handed to a dialog, later a live region or a toast) is a `Reaction` the app does as it drains (`App::drain`); a refused command's number (`SessionError::Refused`) drops the change shown for it; the app's own changes are AppState, never events.
- **What the engine measures for a panel comes as events too** (decision 19): the scopes' readings (`Command::Scopes`, `Event::Scopes`) and readouts, what an operation measures of the photo for its module's panel, the tone equalizer's mask histogram first (`Command::Readouts` naming module and readout, `Event::Readout` with plain data, `None` while the module's operation is not planned). The app asks for the set it shows now, sending a command only when that set changes, mirrors the latest reading, and hands the widget plain arrays of `apertrust-ui`'s own types, never an engine type; a widget asks for nothing. Readings never block a frame: they are counted on the GPU and read back through staging buffers the engine thread polls.
- **Undo and history live in the engine**, as its ordered, serializable list of edits. The UI asks for undo; it never keeps its own copy of parameters as the truth. Widget state mirrors the engine's and is replaced when an event says otherwise. The one overlay: a change the UI has just sent (a value, a reset, a keep, a module's reset) shows until a values report includes that command (`Session::send` numbers commands, `Values::through` says how many a report includes), so a slider never jumps back (decision 17); a lossless view's coordinates and the controls they cover move together in it through the module's pure `view` and `unview` (`modules::Pending::show`), a control's availability with the values through its pure `available` (decision 30), and each change is shown once as it is sent, then again over each report in the order sent.
- **Photos by id** (decision 37). A command that acts on a photo names it by id, as the caption's rating commands do; one that acts on the selected photos (the rating keys, Apply edit, Export) names them all, is one undo step, and the interface shows how many. The active photo and the selection are the session's, so an assistant sees them; the central panel's layout and its cells are the client's.

## Threading model (decisions 17 and 18)

| Thread | Does | Never does |
| --- | --- | --- |
| UI (main) thread | egui, input, presenting the window | wait for the GPU (but inside a reconfigure of the window's surface, decision 18), decode, run CPU-heavy work |
| Engine thread | owns pipeline state and GPU submission for images, every submission through `GpuContext::submit`; renders, waits for the GPU, reads back; the live photo's frame first, then one bounded submission of background work, one step of a job's `GpuTask` chosen by darktable's queue order and ageing (decision 57): an export's (decision 56, its bound set by spike X1) and, with several photos (decision 37), a tile of a still | touch egui or window state; call `queue.submit`; decode a raw, which goes to a job worker (decision 57) |
| Job workers | darktable's workers (`apertrust_base::jobs`, decision 57; the session's export its first caller), 7 or 4: each background job's body (an export's loop, decoding, writing; a folder's listing; import, move, copy, rename, delete), handing its GPU work to the engine thread and waiting through `Context::wait`, its calls into a root through the root's queue (decision 53) | submit to the GPU; hold pipeline state; wait on anything but through `Context::wait`, which returns at cancel |
| rayon pool | CPU-parallel work inside a job or the engine: quantising and encoding an export, decoding's inner loops, thumbnails' scaling | block on I/O: a job's files are written by its worker, edits by the session's edit writer |
| tokio runtime | I/O and the server only | run CPU-bound work |

- **The engine's submissions and eframe take turns** (decision 18). eframe reconfigures the window's surface on the UI thread as the window resizes, and wgpu-core 30 fails a reconfigure, with a panic, when another thread submits during its wait (a wgpu issue, not filed: `Device::configure_surface` waits for the queue to empty and fails if another thread submitted meanwhile). So every submission of the engine's goes through `GpuContext::submit`, never `queue.submit`, holding the device's `SubmitGate`; the app runs eframe inside `Gated`, which holds the gate round every eframe callback; and nothing waits for the engine thread while holding the gate, except through `SubmitGate::released`, as `Session`'s drop does. Holds take turns in the order asked, so each submission waits behind the eframe callback under way, however long it runs: a loop of its own inside a callback, a modal one included, stops the engine's frames until it returns, so such loops run from the run loop, outside eframe's callbacks, as the Mac's popups do (decision 40). The UI thread waits too, for this and nothing else: a callback for a submission asked for before it, a moment, and a reconfigure inside it for the GPU to finish everything submitted, which wgpu-core makes any reconfigure of a shared device do, so a long submission (a photo's first render, an export's tile) makes a resize meanwhile wait for its rest; how long one may run is open (architecture, Open questions). Keep a frame to one turn: record what follows a render in its submission (`Pipeline::render_then`), apart only where a failure must not take the frame with it, as the scopes' count. Uncaptured GPU errors are logged under `gpu`, each kind once, never a panic.
- **Background work is a job** (decision 57): never a thread of its own. Give it darktable's queue (the user's actions `UserForeground`, thumbnails `SystemForeground`, a folder's reading `UserBackground`, export `UserExport`, crawlers and rescans `SystemBackground`), a progress with darktable's message where darktable shows one, cancellable where darktable's is, and check `Context::cancelled` between items; its results go out as its caller's own events, its progress as `Event::Job`. The session's edit writer stays a thread (decision 28).
- **Channels connect them**: commands from the UI to the engine, events back. Use `std::sync::mpsc` or `crossbeam-channel`; no shared mutable state behind locks for parameters or images.
- **Nothing else blocks the UI thread** (decisions 17 and 18). No `GpuContext::wait`, no `pollster::block_on`, no file reading on it: those belong in the session, on the engine thread. The engine thread's own waits must not hold the device either: wgpu holds the device's lock for as long as `Device::poll` waits, and every present needs it, so `GpuContext::wait` never waits on the GPU. It polls without waiting every 0.25 ms until `on_submitted_work_done` fires, sleeping in between without the lock (decision 17). Never call `poll` with a wait, timed or not: a timed wait can also trip a wgpu-core assertion when another thread polls. A readback the UI needs, as the scopes' counts, is mapped without waiting and picked up by polling the same way: while one is on its way, the session waits for commands at most 0.25 ms at a time and looks in between (decision 19; `apertrust-engine::scopes`, engine.md's Scopes); a frame never waits for a mapping, and a readback that fails turns its feature off, never the frame.
- **The engine wakes the UI** when events arrive: `Session::start` takes a closure, which the app makes `egui::Context::request_repaint`, safe to call from any thread, so the engine needs no egui. It is `Send + Sync`, since the edit's writer thread calls it too; the session's `Outbox` calls it, once per burst (decision 59).
- **The engine coalesces commands.** While a slider is dragged, commands arrive faster than frames render. Drain the channel, apply every command to the state, and render only the latest state. Never queue a render per command.

## GPU resource ownership

- **One device** (decisions 17 and 18). The window's wgpu device is the engine's: eframe creates it from `apertrust_engine::gpu::instance_descriptor` (FXC pinned as Direct3D 12's compiler, decision 10) with `gpu::device_descriptor` (timestamp queries, the adapter's own limits), and the engine takes clones of the adapter, device and queue. `wgpu::Device` and `Queue` are `Send + Sync`, so the engine thread and the UI thread submit to the same queue, but never while the UI thread may reconfigure the window's surface: the engine submits only through `GpuContext::submit`, holding the device's `SubmitGate`, and the app holds it round every eframe callback (Threading model above). A reconfigure still waits on the UI thread for the engine's work already submitted.
- **A software adapter is a fallback, not an error** (decision 7). Without a hardware GPU, wgpu gives the engine lavapipe on Linux or WARP on Windows, and everything runs unchanged, only slower. When the adapter reports `wgpu::DeviceType::Cpu`, the app tells the user that editing will be slow; it never refuses to open an image for it, and there is no CPU code path to switch to. The only images refused are those too large for a software GPU even in strips and tiles: on lavapipe, which binds 128 MiB, a raw of about 300 MP or a viewport above about 8.4 MP, and on lavapipe or WARP a raw above 536 MP (decision 7); and on lavapipe, accepted with no engine work planned to remove them, an export whose tone equalizer grid buffer cannot bind (decision 15), one above 8.4 MP whose non-local means reach leaves no tile, bloom (and soften once ported) above about 33.5 MP, filmic rgb's highlight reconstruction above about 8.4 MP and the colour equalizer's guided filter above about 16.8 MP (decisions 7, 13 and 15). Each is an exception the user accepted because only a software GPU binds so little; the refusal names the pass and the sizes. Software-GPU support is to be revisited later, as a whole, when the user chooses. Until then a later port's refusal on a software GPU is accepted the same way, never brought to the user on its own: its spec states the pass and the sizes, it joins decision 7's list in `docs/architecture.md` (GPU processing) and `docs/engine.md` (Limits and errors), and the port and its module go ahead.
- **The engine owns every image buffer and texture.** The UI only holds what it needs to draw the latest frame.
- **Points go through the engine** (decision 16): an on-photo tool (a picker, the crop frame, rotate and perspective's lines, later a mask's shapes) maps frame pixels to an operation's coordinates by `Command::MapPoints`, or by the affine map a frame carries for the focused module; the app never computes an operation's geometry. Which module has focus is view state the app sends the session, never in the edit.
- **Double-buffer the viewport output** (decision 17). The session copies each frame into whichever of its two display buffers it did not publish last, submits, then sends the UI an event naming it. Because both threads submit to one queue, the UI's drawing is ordered after the copy that its event names, and a published buffer outlives the pipeline that rendered it. A buffer holds frames of one size only, so a frame is never drawn with another's dimensions.
- **Size buffers to their use and free before replacing.** At 60 MP one RGBA f32 buffer is about 1 GB: drop the old buffers before allocating new ones, as `Pipeline::update` does when a plan's shape changes and the session does with its display buffers. What still holds moves instead of being freed: a rebuild over the same input keeps its compiled kernels and every cache point whose key and size still match (decision 28), so an operation joining after the downscale, or a larger viewport, does not run the raw stage before its first cache point again; a larger tiled viewport still reruns demosaic's tiles, and a change that reaches the raw stage, even one arriving with a join, still reruns it.
- **Render at viewport resolution while editing** (decision 8 and the viewport spike): a single full-resolution pass already takes 27 ms on the M4 and the Radeon 780M. Full resolution is for export and the visible region at 100%.
- **Preview first.** When the preview pipe and a full pipe (export, a 100% region) compete, the preview's latest state renders first; stale full-pipe work is cancelled or deprioritised rather than finished.
- **One live photo, the rest stills** (decision 37, planned until spike W1 measures it; engine.md, Session and threads). One session per window; the client sends the visible cells, each a photo id and a size. Only the active photo has a live pipeline. Every other cell is a still, the viewport pipe at the cell's size rendered once from the saved edit, its frame kept and its pipeline freed, and drawn by the same paint callback; a still equals the live frame at its size byte for byte. Background work is one tile per submission, so a change waits for one at most; compiled kernels live as long as the session; one budget covers the live pipeline and the stills, stills dropped first. Never a session per visible photo: 1.5 to 4.9 GB each, and an edit waiting behind other photos' first renders.

## egui patterns

- **State lives in the app struct; the UI is rebuilt each frame** from it. Never store per-frame values (sizes, hovered items) as state; never derive state from the UI's previous frame.
- **The viewport is a paint callback** (decisions 17 and 35): our own render pipeline (`crates/app/src/viewport.rs`) reads the engine's latest frame from its storage buffer inside egui's frame, each physical pixel its own frame pixel, with full control of encoding for the surface format (needed for float16 and EDR output later) and room for on-image overlays. Its shader is WGSL, validated with naga in a test: a display shader needs none of Slang's derivatives.
- **Show the image one texel per physical pixel** at fit-to-window: render at the panel's size times `pixels_per_point`, place its corner on the physical pixel grid, and sample nearest. At fractional scaling, anything else blurs the whole image. The one exception (decision 18): while the window resizes, or the side panel's edge moves, the engine is not asked for each size, and a frame rendered for another size is shown bilinearly scaled to the size its successor will have (`Photo::viewport_size`), until that arrives.
- **Repaint only on change.** egui repaints on input; the engine's frame-ready event requests a repaint otherwise. No continuous repainting to poll the engine.
- **Module panels come from module definitions** (Phase 2, decision 28), not hand-written per module: the renderer in `crates/app/src/modules.rs` draws a section from the definition's controls, tabs and rows, the session mirror giving each control's value, default, mark and whether it can change the photo, and returns `Change`s: the module commands, which the app sends through its pending values, and the section's open state and tab, which it keeps (`docs/gui.md`, Module panels from definitions; `ui-conventions` covers their look, `tool-bindings` what they do).
- **Components come from `apertrust-ui`** (`docs/gui.md`, decision 36): a builder with `show(ui) -> Output` that draws its value and reports what the user did. The app turns outputs into session commands or UI intents, and applies intents after the frame, so a frame never reads half-updated state.
- **Actions are declared once**, in the app's actions registry, `ACTIONS` in `crates/app/src/actions.rs` (id, message, default keys, scope, availability, what it emits: a session command or a UI intent); buttons, menus, tooltips and the keyboard handler all read it, and an action that can't run is drawn disabled. `actions::read` takes the frame's keys out of egui's input before anything is drawn, leaving the focused widget its own keys; keys and clicks then run after the frame through `Shell::run`. Never handle a shortcut inside a widget: a widget that reacts to a held key is told it is held (`Section::peek`). Match keys as `actions` does (the logical key; the physical digit first on the number row; exact Alt and Shift; a letter skipped when its press typed another key's character, which is how AltGr arrives, since egui never sees it as a modifier), check a new key against the others with `actions::conflict`, and spell keys with `Shortcut::spell`, never by hand. Settings keep keys in `Shortcut::text`'s portable form (`Ctrl+Shift+Z`, Ctrl being Cmd on macOS and Meta a Mac's Control key), read with `Shortcut::parse`; `Keymap::set` changes an action's keys and what settings keep of them (`Keymap::overrides`), and `Keymap::load` refuses an override that clashes. Native menus never own a key (decision 39): on the Mac they carry the keymap's keys as key equivalents and run the registry's actions, and while a widget has focus they hold none of the keys `Focus::keeps` gives it; Undo, Redo, Cut, Copy, Paste and Select All act on a focused text field (egui's `RequestCut`, `RequestCopy`, `RequestPaste`, and keys added through `raw_input_hook`). A hold action is never a menu item. The platforms' menu keys and, on Windows and Linux, Alt with a letter are refused for actions, as the clipboard's are: built on Linux, where `Keymap::load` refuses Alt with a letter (`opens_menu`) and keeps F10 for the `menu` action. Alt with a letter is read by `actions::access_key` before `actions::read`, the letter typed on the current layout first, then the key's own Latin letter, and taken out of the frame when a top-level menu has it as its access key.
- **Platform services sit behind traits** (settings storage, `apertrust_base::settings::Storage`; files, clipboard, the engine connection), so the browser build can swap them (decision 35).
- **UI colours are authored in sRGB**, and the window is tagged sRGB by `apertrust_display::tag_window` every frame, because wgpu leaves it untagged and macOS then shows it without colour management.

## Platform integration

- **File dialogs**: rfd, with its `xdg-portal` backend on Linux (nothing compiled in: since rfd 0.17 it loads the system's libdbus at run time, as winit loads libwayland, both platform libraries outside decision 5's rule), through its async dialogs or opened from the run loop: a blocking dialog inside an eframe callback runs a modal loop that holds the submit gate and stops the engine's frames until it closes (decision 18). Where no portal answers, rfd runs zenity instead; with neither, a dialog that cannot be shown answers as a cancel would.
- **Dialogs are native modal windows** (decision 41; `docs/gui.md`, Dialogs and alerts): every dialog (Settings, Export, Customise tabs, a prompt for a name) is a window of its own, modal to the window it rises from; About and a future splash screen are the only egui modals over the window, the exceptions. Never draw a new dialog with `egui::Modal`.
  - The app hosts the windows beside eframe's: `Gated` creates each one, hidden, with an egui-winit `State` and its AccessKit adapter made before it shows, an egui `Context` of its own (the app's fonts, theme, language and scale set on it too), and a surface and egui-wgpu `Renderer` on the engine's device from eframe's `RenderState`.
  - `Gated` routes the window's events, `UserEvent::AccessKitActionRequest` and `UserEvent::RequestRepaint` with the host's viewport ids to the host, never to eframe. Everything runs inside the gate's held callbacks.
  - Not egui viewports: eframe 0.37 gives the app no viewport's window and a child window no AccessKit (an eframe limit: its native wgpu integration sets up AccessKit for the root window alone, and offers a viewport's window no owner, parent or modality).
  - Modality is the platform's: winit's `with_owner_window` and `set_enable` on Windows; `apertrust-display` for the Mac's sheets (`beginSheet:completionHandler:` and `endSheet:`, each animating the sheet in a run loop of its own, so started from the run loop, never inside a callback; the sheet where AppKit puts it, centred), Settings a modeless window of its own, X11's transient-for and modal state, and Wayland's parent and xdg-dialog. The app also takes the main window's input while one is open.
  - **A dialog is one type implementing `dialog_host::Dialog`**, the same on every platform: `id`, `title` (translated), `form(os)` (`Form::Sheet`, `Modal` or `Modeless`), `look` (background and margin; every window takes its content's size), `keys(os)` (what Escape, Cmd+W and Cmd+. do; the host applies them after the content, leaving Escape to a field typed in and to a list the content says it holds, `Asks::keeps_escape`), `show(&mut Ui) -> Asks` and `placed` (an `Output` for a modeless window whose place is kept). The host knows nothing else of a dialog: no per-dialog `match` in it. Each platform's part of each form is in `dialog_host::platform` alone: `platform::form(wanted, os)`, pure and tested for macOS, Windows and Linux, a sheet the Mac's and a modal window elsewhere, and `platform::attributes`, a modal window owned by the main window on Windows and of the dialog type on X11. To add a dialog: implement `Dialog` beside its content, add its `Output` variant and handle it in `take_dialogs`, open it with `AppDialogs::open` from `run_action`, test its content through `dialog_host::draw` and the app's side through `main.rs`'s `FakeHost` (which can give each dialog its platform's form, `FakeHost::on`). Under a sheet or a modal window the app takes the main window's input (`under_modal`) and a press on the main window brings a modal window forward (`Dialogs::raise`, not while an alert asks) on every platform; the keys a dialog's window leaves alone come up as `Output::Keys` and run through the app's keymap in `take_dialogs` (`actions::read_from_dialog`), so Ctrl+Q works from any dialog (`docs/gui.md`, How a dialog is built now).
  - A dialog's content is a function of `&mut Ui`, tested in a harness of its own (`dialog_host::draw`, as the host draws it each frame); the app reaches the host through a trait, `Dialogs`, as `OpenDialog`, and the tests drive a fake of it. What a content changes for the app (Settings' theme and language) comes back as `Output`s, which `App::logic` hands the shell before the next frame (`take_dialogs`); its window takes the content's size, measured as it is drawn. A dialog's buttons go through `dialog_host::buttons`, at the row's end in the platform's order, laid out from its start so screen readers and Tab meet them as they are seen; never egui's right-to-left layout for them. A dialog that needs the session reaches it through the app, never directly: it asks with an `Output` (Export's is `Output::Export(Asked)`, the settings changed and whether Export was pressed, which `take_dialogs` hands back as `Taken::export` and `App::export` turns into `PreviewExport` and `Export` commands with `export::commands`), and the session's answer comes back through `Dialogs::preview` to the dialog open.
  - Built on the Mac (decision 41, `crates/app/src/dialog_host.rs`): Settings is a modeless window of its own, with no Close button, Escape doing nothing and Close Window (Cmd+W) closing it, as Apple's are, opening where the user last left it (the app's `settings_window.position`, which the host reports as `Output::Placed` as it closes and restores through the main window's own `on_screen`) or centred the first time; Windows and Linux show it as a modal window of the host with its Close button, Escape closing it. Every dialog window is kept out of other windows' tabs (`apertrust_display::keep_out_of_tabs`). The jobs window (decision 57) is the host's second slot (`Slot::Jobs`): a modeless window that stays open beside Settings or the Export sheet, with its own place (`jobs_window.position`, reported as `Output::JobsPlaced`), repaints (`jobs_viewport`) and AccessKit tree; it follows the main window's theme and language, its content is `jobs::Window`, and what it fills from is the app's `jobs::Mirror`, folded from `Event::Job` and `Event::Export` by the app's mirror (`mirror.rs`); its buttons come back as `Output::Jobs`, run by `Mirror::act`. The host holds eframe's window weakly: a clone keeps it from being destroyed, and eframe's loop then never ends. `begin_sheet` and `end_sheet` schedule AppKit's calls on the main run loop with `performInModes:block:`, which wakes the loop (`CFRunLoopPerformBlock` alone would not), since each runs its 177 to 206 ms animation in a run loop of its own, which inside a callback would hold the gate; they call back once AppKit's call has returned, the phases one pure, tested function (`dialog_host::step`), and the host keeps a sheet's window until `endSheet:` has, reporting the dialog shown until then, and holds a close asked while the sheet slides in. Quit, Close Window on the main window and the main window's close button (held with `ViewportCommand::CancelClose`) close the dialog as its Cancel and leave once it has gone, as AppKit closes no window a sheet hangs on. A modal dialog takes the main window's input without adding an event to every frame, which would make the window draw for ever. `State::modal` (a sheet or a modal window of the host's, About, the open dialog asking) rests every action that opens a dialog, and `State::dialog_window` (a modeless dialog's window with the focus) the view's keys and the menu items that act on the main window, as AppKit's responder chain would; the main window's own controls are drawn from a state without the dialog's focus (`App::state_in_window`), as AppKit checks a window's controls against that window. Quit waits for the open dialog's answer, since a Quit under AppKit's panel leaves the app running.
- **Confirmations are the system's alerts** (decision 41): one alert service of plain requests (title, message, buttons with words and roles: default, cancel, destructive), answered on a later frame (`apertrust_ui::alert::Request`, asked through the host's `Dialogs::ask` and answered by `Dialogs::answer`; the app's confirmations and their decisions in `crates/app/src/alerts.rs`). On the Mac an `NSAlert` sheet (built), on Windows `TaskDialogIndirect` on a thread of its own (Common Controls 6 through a linker-embedded manifest), on Linux Apertrust's own alert in a dialog window (proposed). Words are Fluent's, never the system's OK and Cancel. A request may carry a suppression box ("Don't ask again", `Request::suppression`), reported with the answer; what ticking it turns off is a setting, kept with a yes only. Not rfd's message dialogs, which run zenity on Linux.
- **Window frame** (decision 39, `docs/gui.md`, The window frame and menus): the top panel runs to the window's top edge on every platform and is the title bar. On the Mac a full-size content view with a transparent title bar; the traffic lights stay AppKit's, placed by `apertrust-display` after every layout. On Windows and Linux decorations off, caption buttons drawn by the app; the system still moves the window (`StartDrag`, never on the press, so a double-click stays one), resizes it (`BeginResize` from bands inside the edges) and opens its window menu (winit's `show_window_menu`, through the window `CreationContext::winit_window` hands over); Windows' snap layouts flyout needs native hit testing (`WM_NCHITTEST` answered with `HTMAXBUTTON`), which `apertrust-display` adds as a second step. `TopPanel` stays platform-free: told its inset and whether to draw caption buttons, it reports drags, double-clicks and right-clicks on its empty areas. Never `with_movable_by_background(true)`: dragging a slider would move the window. The Mac's frame is built: the app calls `apertrust_display::place_window_buttons` each frame with the top panel's height in the window system's points (egui's times the interface's scale) and hands the room it returns (`WindowButtons::Placed`, or `Unplaced` where the views are not as expected, the top panel staying the title bar either way) to `TopPanel::start_inset`; the first call also replaces the title bar container's `layout` and winit's window's `setFrame:display:`, so AppKit's own layouts, on every step of a zoom or a resize while egui draws nothing, put the buttons back before they are drawn; it calls `content_never_moves_window` once the window exists, since AppKit otherwise moves the window from a drag begun anywhere under the transparent title bar, a button included; it runs `TopPanel`'s `MoveWindow` and `TitleBarDoubleClick` after the frame through `run_title_bar` (`start_window_drag`, which hands AppKit the press's own mouse-down and logs under `-d gpu` what it handed over, else `StartDrag`; the next frame then gets the release the system may keep, `release_after_drag`; `title_bar_double_click`, then `zoom_window`, which starts the zoom from the run loop so each step of AppKit's animation is drawn, else `Maximized`; or `Minimized`), never inside the widget. While the window resizes, the app holds the photo's new size from the engine until the window has kept its size for 150 ms (`Bounds`, decision 18), the engine being unable to render each step in time, and draws the last frame scaled to the size the next will have (`Photo::viewport_size`). Use the system's title bar, a setting on Windows and Linux, off by default, turns decorations back on live (`ViewportCommand::Decorations`); on GNOME it then gets winit's Adwaita frame through the Linux-only feature `wayland-csd-adwaita-notitle`, never `wayland-csd-adwaita`, whose title renderer brings ttf-parser, which `cargo deny` refuses as unmaintained. The window's minimum width is 500 points, so Windows 11's snap zones take it; it is lowered in code once the shell gives way below 960.
- **Menus** (decision 39): one model, `MENUS` in the app, naming registry actions as `TOP_PANEL` does. On the Mac, muda's native menu bar (a macOS-only dependency, default features off; its macOS API needs no `unsafe`), replacing winit's default menu, with only the system's own items predefined (Services, Hide, Hide Others, Show All, Minimise, Zoom, Bring All to Front) and everything else, About and Quit included, a registry action, so Quit leaves through the app's exit path. On Windows and Linux, one menu button, ☰, at the top panel's very start, before the mark, with no row of titles (decision 39): `TopPanel` draws it (`menu_button`) and reports `Menu`, and the app opens `MENUS` as one pull-down of submenus through the popup service, drawn there (decision 40); there is no `MenuBar`. Built on Linux (`Shell`'s `drawn_menus`): `menus::request` builds the request each time the menu opens, from the keymap and `State` (the words, enabled, the first key whatever has the focus, check marks from `Action::checked`), `menus::chosen` turns the id chosen back into its action, and `Shell::popups` calls `popup::show` once a frame on every platform and reads the answer, run after the frame through `Shell::run`; the `menu` action (F10, `Platforms::Linux`) and Alt with an access key (`Shell::access_key`) open it, and it closes when a key runs an action or a dialog opens. Windows' ☰ comes next. muda's Win32 menu bar lives in the non-client area an integrated frame removes, and on Linux it would pull in GTK. Menu choices come back through muda's event handler (a channel and `request_repaint`) or the popup service's answer, and run through `Shell::run`, like clicks and keys; the Mac's in `App::logic`, which eframe calls alone while the window is minimised or hidden, so Quit never waits for the window to show, and a press action's choice by a held key's repeat is dropped (`apertrust_display::handling_key_repeat`). Push only what changed into muda each frame. Turn winit's default menu off on the app's own `EventLoop` builder in `main` (`with_default_menu(false)`): eframe runs on the app's loop (`Gated`) and ignores `NativeOptions::event_loop_builder`.
- **Popups** (decision 40, `docs/gui.md`, Popups): a component never opens a list itself; it sends a plain request (anchor, kind, items) to the popup service in egui's context and reports the answer when it arrives, a later frame. The drawn service in `apertrust-ui` is the default (tests, gallery, browser, Windows, Linux): `apertrust_ui::popup`'s `open`, `show`, `answer`, `close`, `is_open` and `anchor`, each level an egui `Area`, never egui's `Popup`, and an egui plugin taking an open popup's plain keys and text out of the frame's input before egui reads it (F-keys and keys with a modifier stay the app's); the app must call `popup::show` once a frame, since the plugin cannot draw, and a popup no pass draws closes and takes no keys; an answer is read once. Built: the pull-down and the dropdown, `Choice`'s list with darktable's type-to-filter (`Choice` calls `popup::show` itself while its list is open, a second call in a pass doing nothing, so it reads the answer in the frame it arrives); ⋯, » and ⋮ go through it too (`components::pull_down`), and a slider's fine control a kind of its own, drawn on every platform (decision 42), and a request names its opener (`Request::opened_by`), the control the focus goes back to, since a press leaves egui's focus on nothing. A `popup::Service` installed in a context (`popup::install`) takes the requests it says it takes, the rest drawn; it answers between frames with `popup::answered`, which the next frame's `popup::answer` gives, the focus back on the opener. Built on macOS: the app's native service (`crates/app/src/popups.rs`), installed on the main window's context in `App::new` and on each dialog window's by the host, which only holds a request in the frame; `popups::show(ctx, window)` after the frame turns it into `apertrust_display::PopUpMenu`, the display crate's own plain data (it depends on nothing of ours), and `apertrust_display::pop_up_menu` builds the `NSMenu` (`autoenablesItems` off, items' target an object of its own class noting the tag chosen, so the menu runs nothing; keys as key equivalents for show; the theme's Aqua or Dark Aqua) and shows it with `popUpMenuPositioningItem:atLocation:inView:` (the checked item over a dropdown's control), scheduled on the main run loop, never inside winit's event handler, where a menu's tracking loop would freeze the window and hold the submit gate. Not muda's context menus. Tests install a recording service (`crates/ui/tests/service.rs`). Anything that previews on hover or holds controls, colour, thumbnails or a search field is drawn on every platform.
- **Display colour**: all per-platform colour-space code lives in `apertrust-display`, behind one function per need.
- **App paths and settings**: Apertrust's folders through one place, `apertrust_base::folders` (`Folders`, behind base's `folders` feature, on the `directories` crate), never hand-built paths; add a folder there when something is first kept in it. Each binary reads the flag from its own command line into a `folders::Given` (the app's `arguments`, as it reads `-d`; the CLI's with clap) and calls `Folders::find` once, after the log starts and before anything is read; an `Err` stops the start. A program that only reads there, the CLI, calls `Folders::find_to_read` instead, which creates and probes nothing: one given that is missing or unreadable is the error, and a missing platform folder gives the defaults. The person's own folders the app looks in, Pictures for the open dialog, stay in `crates/app/src/paths.rs`. Two folders (decision 43; `docs/architecture.md`, Settings and folders): the **user data folder**, holding the person's settings and personal resources (`settings.toml`, `state.toml` for Open Recent, `themes/`, later scripts, styles, presets, `presets/export.toml` the first (decision 56), and crash reports), and the **cache folder**, holding what can be computed again; no other platform folder is used, so one folder holds a person's whole set-up, `~/.config/apertrust` on Linux, never split by XDG kind. The library never goes in the user data folder: it lives in another place, next to the images, its place and form decided with its design (Phase 5). The user data folder is `--user-data-dir` (`--config-dir` and darktable's `--configdir` accepted), then `APERTRUST_USER_DATA_DIR`, then the platform's, where settings are today; one given explicitly keeps its cache inside it, as `<user data>/cache`, and never falls back to the platform's folder when it cannot be used. **Edits** (decision 47; `docs/architecture.md`, Edits in another user data folder): beside the photos in every user data folder (decision 48), or in a library's own folder as each root's id file says, never decided by the user data folder (decision 47), so there is no `engine.edits` and no `edits/` tree in a user data folder: a separate folder, Apertrust Dev's too, separates settings only, and a development build that understands an edit can still change it. No build overwrites an edit a newer Apertrust wrote, told by what it holds, never by comparing versions. That is anything in it a save would drop: a newer file or module version, a module neither known nor retired, and, planned (decision 48), a control, value, operation, parameter or element this build cannot keep at the edit's own versions. Versions rise for removals and changes, never for additions (`docs/engine.md`, What a save may drop): the photo opens for viewing only, saying which version wrote it, and every edit records the build that wrote it. **Settings are declared once, in the settings schema** (`data/settings.schema.toml`, decisions 43 and 45, replacing hand-written reading and writing as its build plan lands), never in Rust: a TOML table per setting, its header the id (the dotted key in the file), with `owner` (`app`, `engine`, `export` or `module:<id>`), `kind` and its range, step, decimals and unit, `default` (or `"computed"`, computed in Rust), `page` and `group` or none, `applies` and platforms, a `#` comment a developer's note, and no English: its words are message ids that follow from its id. A choice names its Rust type (`type = "apertrust_ui::Builtin"`), which implements `Choice`, each value's stable id; never list its options in the schema. Each owner's crate generates its own settings in its `build.rs` as typed statics (the app's, the engine's as `apertrust_engine::settings`, the export settings as `apertrust_export::settings`, tools' in `apertrust-modules`), read with `settings.get(&KEY)`, written with `settings.set(&KEY, value)`; a new setting is a table in the schema, in the place the dialog shows it, and the build refuses an unknown field, a wrong kind or a default out of range. The engine never opens a folder or reads a settings file: the binaries read the store and hand it options (`apertrust_engine::settings::Options::read(&store, &flags)`, `GpuOptions` and the budget, each value logged under `-d settings` with where it came from); the app opens one store on its registry and the engine's together, the CLI a read-only one on the engine's and the export's (`Store::read_only`, which borrows its storage, so it never writes, sets aside or tidies), its `export` taking from the export settings only what darktable-cli takes from darktablerc, the format's options, its own flags the rest, and a binary's own flag (`--adapter`) comes before the file; the golden harness reads none, taking `GpuOptions::default()` and `pipeline::BUDGET`, the settings' defaults, and a script that times the CLI gives it a user data folder of its own (`APERTRUST_USER_DATA_DIR`), as `tools/compare-cpu.sh` does. The session takes the budget as it starts (`Session::start`). An adapter a setting names that is not there falls back to wgpu's choice with a warning, as decision 7 has it; one a flag names is an error. A developer's switch (`--max-binding`, `-d`) is a flag, never a setting. Settings are one versioned TOML file, `settings.toml` in the user data folder, migrated as `.apxmp` is: theme, locale, scale, key overrides, workspaces (the side panel's named sets of tabs) and each layout's state, never edits nor the last photo (`docs/gui.md`, Settings and workspace). `settings::Keeper` reads it once in `main`, before the window opens, so `NativeOptions` and the first frame have it; the app hands it `Shell::to_settings` each frame, and it writes only once they have stood still for a second, and on exit, on its own writer thread, as the session writes edits, so no file is written on the UI thread. The writer reads the file again and writes only what changed since its last write, so values it cannot read, unknown keys and another instance's changes stay. The store, `apertrust_base::settings::Store`, gives every setting these rules. A new setting of the app's is a table in the schema, a field in the app's `Settings`, and its line in `Settings::read` (`store.get`, or `store.kept` for one kept only once the user sets it) and in `Settings::write` (set only where it differs from the app's reading of the store, and a reset for None); the every-key tests in `crates/app/src/settings.rs` fail until their `everything()` sets it and the byte-for-byte file has its line. Set only on the user's action a setting whose default is computed, as the language: `set(get())` keeps it, and it no longer follows what it is computed from. The shell reports a setting as read until the user changes it, as it does the language and the side panel's tab, so an unreadable or unknown value is not replaced unasked. Never overwrite a newer version's file. The window is placed after creation from `CreationContext::winit_window` (`place`, as egui-winit's `WindowSettings` does), and the scale is set in egui's options before the first frame, never with `set_zoom_factor`, which applies a frame late.

## Errors and logging

- **One error type per library crate**, with `thiserror`, as the existing crates do; `anyhow` only in binaries and the harness.
- **User-facing versus internal**: an error the user can act on ("this raw format is not supported", "the GPU ran out of memory") becomes an event the UI shows in plain words; everything else is logged with its context and shown as a short failure.
- **Logging is darktable's `-d`** (decision 44, `apertrust_base::log`, behind base's `log` feature, decision 43): silent but for warnings and errors; `-d gpu`, `raw`, `pipe`, `perf`, `memory`, `golden`, `settings` (the user data folder, the settings file and the engine's settings read) `control` (each job added, run, discarded or cancelled, decision 57) or `event` (each event the session sends and each drain, decision 59; `signal`, darktable's name, an alias, as base's `log::ALIASES` holds it) switches a domain on, on stderr, with `all` and `verbose`; every binary takes them and calls `apertrust_base::log::init`, keeping the `Logging` it returns until it ends, then `apertrust_base::log::starting` with its `apertrust_base::program!()` and its build list. A line is the seconds since start, `[domain]` and a short phrase (decision 44).
- **The startup banner** (decision 44), as darktable's, on stderr only and only with a domain on (`RUST_LOG` too), in the app as in the CLI and the harness: the program and version with the commit (`0.1.0+128~g60867cf-dirty`) and `[os arch profile]`, the copyright and licence, a `Build:` list in darktable's columns, where to read and report (`apertrust_base::log::REPOSITORY`, the workspace's `repository`), then `[starting] as:` and the command line. `--version` (or `-V`) prints the same banner without the command line on stdout, in every binary, as darktable's does: each `main` checks `apertrust_base::log::version_asked()` first and passes its `build()` list to `print_version`. Versions come from the build, never typed, and from each binary's own: its `build.rs` calls `apertrust_base::build::version()` (base's `build` feature, a build-dependency), which reads `Cargo.lock`, the Slang pin in `tools/fetch-slang.sh` and Apertrust's own version from the newest `release-X.Y.Z` tag at or before HEAD with the commit (`crates/base/src/build/version.rs`; `APERTRUST_VERSION` for a packager; never `Cargo.toml`'s, so never `CARGO_PKG_VERSION`) and hands them to the binary's compiler, where `apertrust_base::program!()` reads them: the version is `program!().version`, never a library's constant, so a commit rebuilds the binaries' packages and no library. The script runs again only when HEAD, a tag or `shallow` changes, since the binary's package rebuilds with it; so `-dirty` says whether tracked files had changes when HEAD last moved. A library or feature that matters for support gets a line from the log's helpers, each given the `Program` (`wgpu`, `rawler`, `kernels`, `Item::package`), a new library's package added to `PACKAGES` in `crates/base/src/build.rs`; one this build lacks, `Item::disabled` with what is missing. `starting` asks for the list only when it prints, so a line may look something up (the harness's darktable-cli version). `-d gpu` then lists the adapters, the chosen one marked, with its driver and limits (`gpu::log_adapters`).
- **Writing a log line**: `tracing` with the domain as the target, never a module path: `tracing::debug!(target: "perf", "rendered {} in {:.1} ms", …)`. `debug!` for a domain's line, one per user-visible step (decode, plan, compile, render, write); `trace!` for the detail `verbose` adds (each parameter, each buffer, each pass); `warn!` for what still works but worse (a software adapter, an untagged window); `error!` for what failed. No `println!` or `eprintln!` in library crates; a binary's stdout carries only its results. A new domain goes into `apertrust_base::log::DOMAINS` first.
- **How a line reads** (decision 44): terse, as darktable's, never a sentence. Lowercase, the fact first, then details as `key: value` pairs, separated by commas; the whole line, time and domain included, within `apertrust_base::log::WIDTH`, 100 columns, in the common case. Units and readable values (ms, MiB, EV; `ImageDesc` prints `9600×6376 RGBA`), never `{:?}` dumps. A file's whole path in a warning or an error, which show without `-d`, so the person learns where it is; its name alone in a debug or trace line (`apertrust_base::log::file_name`). A list goes on a summary line at the domain's level and one line per item at `trace!` (`rendered 22 passes from rawprepare in 682.5 ms, GPU: 185.7 ms`, then `pass rawprepare: 3.0 ms`); a long run of short items, as an operation's parameters, packed into lines that fit, each starting with the same head (`agx params: …`). A warning says what failed and what follows, in few words. An error is never cut: another crate's text in one of ours, as a wgpu error over several lines, goes through `apertrust_base::log::one_line`, its innermost cause last. Other crates' own lines (rawler's through `log`) are handled by the log: an error on one line, anything else cut at the width with "…" keeping the innermost cause, whole under `verbose`; the same line repeated is written once, then again with `(repeated N×)`; rawler's lens lookups are one line of the raw domain, since Apertrust does not use the lens yet. No debug line inside a per-pixel or per-frame loop. For example:

  ```text
      0.2780 [perf] decoded B13A0729.CR2 in 277 ms
      0.2781 [raw] Canon EOS 5D Mark IV: 6880×4544 RGGB, active: 6744×4502 at 136,42
      0.2857 [gpu] adapter: Apple M4 (Metal, integrated)  <- chosen
      0.3049 [pipe] plan: export, 8 ops, 22 passes, 6720×4480 RGBA
      0.3049 [memory] buffers: 1989 MiB (work 1150, scratch 779, input 60)
      1.3538 [pipe] rebuild: plan changed, kept 23 kernels, cached: demosaic, downscale
      0.2778 [raw] lens: not identified by rawler
      2.1033 [settings] warning: cannot write /Users/you/Library/Application Support/Apertrust/settings.toml: No space left on device (os error 28); retried on the next change
  ```
- **Crash reports**: a panic hook writes the banner (`apertrust_base::log::banner`, whatever the switches; decision 44), the panic, backtrace and recent log to the user data folder's `reports/` (decision 43) and offers to show it on the next start; a log file, when it comes, starts with the banner too. What a report leaves out of the whole paths it carries is decided when it is built. Nothing is sent anywhere without the user's consent.

## Profiling

- **puffin for CPU time per frame** (decision 17): `puffin::profile_function!` and `profile_scope!` in engine and UI code worth watching, with the puffin viewer behind a debug toggle in the app.
- **GPU timestamps for GPU time**: the engine's `GpuTimer` gives per-pass times; puffin cannot see the GPU.
- **Finding what blocks a frame**: compare the frame interval with the UI thread's puffin scopes. Time on the UI thread outside egui's own scopes is usually a wait that belongs on the engine thread.
- Tracy is not used: its client compiles C++ (decision 5).

## Packaging

Phase 7 (`docs/architecture.md`, Platforms and language):

- **macOS**: an app bundle, signed with a Developer ID and notarized. Until then the binary carries `crates/app/assets/macos/Info.plist` (`build.rs`), so an unbundled run's menu bar reads Apertrust; the bundle's Info.plist takes its place. The Dock reads "apertrust" until the app runs from a bundle: it names an unbundled app after its executable's file, which no plist key or public call changes (`docs/gui.md`, The menus).
- **Windows**: an installer or MSIX, code-signed. The build uses MSVC; nothing may need another toolchain (decisions 5 and 23).
- **Linux**: Flatpak and AppImage. Large GPU and AI runtimes load at run time instead of being bundled; acceleration packs download on demand. Neither package ships the platform's libraries (decision 5): the Flatpak takes them from its runtime, the AppImage from the system, its bundling step excluding the Vulkan loader, libwayland, libxkbcommon, the X11 libraries and libdbus, since a bundled one would be Apertrust's to ship, under decision 5.
- The UI's fonts are compiled into the binary, so every package ships their licence, `crates/ui/assets/fonts/OFL.txt` (decision 36).
- The app icon is in `crates/app/assets/icons` (its README says which file each platform uses): the `.icns` goes into the app bundle, the `.ico` into the Windows executable's resources, and the hicolor tree into the Linux icon theme, named after the app id. The window's icon is compiled in separately. Icon files carry no embedded metadata.
- Bundled data (camera definitions, lens database, models) goes in the platform's resource location, found through the app-paths helper, never by a path relative to the source tree.

## When a change does not fit

If a task needs to break one of these rules (a new thread, a blocking call on the UI thread, a C dependency, engine code that knows about egui), stop and say so: the fix is usually a different boundary, and if the rule itself should change, that is an architecture decision for `docs/decisions/`, made with the user.
