# Port a darktable module

Porting is the migration (decision 2): Apertrust builds on darktable's trusted colour science by rewriting darktable's processing modules, and the migration ends once, for the whole project, when every first-pass module is in the app and passes its comparisons, at the end of Phase 3. Until then darktable's code is the **reference**, never a dependency: never link, load, wrap or call darktable modules. After it, Apertrust's own renders are the baselines and its processing may evolve on its own (`golden-tests`, Baselines and tolerances); a ported file keeps darktable's copyright and provenance. What ships runs as GPU-resident Slang kernels, which is what makes the pipeline fast, differentiable and portable.

During the migration darktable plays two roles, and only these two:

- **Reference source:** its code defines the maths, parameters, edge cases and behaviour we reproduce.
- **Reference output:** `darktable-cli` renders are what the golden-image harness compares against.

Every port follows the same four steps, in order. Do not skip the spec, even for small modules: it is what makes the kernel reviewable and the differences intentional. `docs/ports/colorbalancergb.md`, with its crate `crates/op/colorbalancergb`, shows the finished shape of a port.

## Where things live

Each operation is a crate of its own, `apertrust-op-<module>` in `crates/op/<module>` (architecture decision 20); its manifest and schema are in `src/lib.rs`.

| Item | Path |
| --- | --- |
| darktable checkout | `$DARKTABLE_SRC`, your clone of darktable, such as `../darktable` beside the checkout (its `upstream` remote is darktable-org) |
| Reference release | darktable's latest stable release (decision 3, AGENTS.md), its number in `REFERENCE_VERSION` in `crates/golden/src/darktable.rs`, its tag `$DT_TAG` (set in Step 1); never port from a newer checkout |
| Port spec | `docs/ports/<module>.md` |
| Slang kernel | `crates/op/<module>/slang/<module>.slang`; shared colour maths in `crates/color/slang/color.slang`, the pass header in `crates/plugin/slang/pass.slang`, `add_at` and `set_at` in `crates/plugin/slang/components.slang` |
| Generated WGSL (committed) | `crates/op/<module>/generated/<module>.wgsl`, from `tools/build-kernels.sh` |
| CPU-side setup | `crates/op/<module>/src/setup.rs` (`Settings`, `prepare`, `NotPorted`), re-exported by `src/lib.rs` with the `KERNEL`; shared CPU colour maths in `crates/color` |
| The list of operations | `KERNELS` in `crates/operations/src/lib.rs`, which also re-exports each operation crate |
| Golden case | a `Case` in `crates/golden/src/cases.rs`, its sidecar in `crates/golden/cases/<case>.xmp` |
| darktable parameters to kernel inputs | `crates/golden/src/ports.rs` |
| Architecture decisions | `docs/decisions/` (the decision log, one file each) |

`<module>` is darktable's operation name (`exposure`, `colorbalancergb`, `toneequal`), so provenance stays obvious.

## What to port

A port takes a module's processing path, not the whole file: darktable's GUI code (the widgets, the curve graph, the pickers and warnings) stays behind, and its presets become presets in the spec's tool binding notes. What darktable's GUI computes from the image, usually from the preview pipe (the tone equalizer's mask histogram, RGB levels' and RGB curve's input histograms, `request_histogram`), is no GUI code to leave behind: note it in the spec as a readout, the operation's own pass and decode, restating darktable's arithmetic, built with the module's panel (decision 19; `docs/engine.md`, Readouts). Within the processing path:

- **Every continuous parameter.** They are numbers in the same maths, so they cost little, and the module's controls, golden cases and later bindings all reach them.
- **An alternative mode**, a second algorithm chosen by an enum (AgX's base primaries from the export profile), only when a binding or a module needs it, or the user chooses it as the better algorithm; ask when unsure. Otherwise `prepare` returns `NotPorted` for it, a test covers that, and the spec lists it under Deliberate differences. The mode darktable gives a new instance is never an alternative: it is ported with the operation, as colorbalancergb's darktable UCS was (decision 22).

**The module in the first pass** (decision 2): the operation's module mirrors the darktable module: every control its interface shows, in darktable's order, ported or not, under darktable's label, starting at the photo as first shown (decision 29). The spec's tool binding notes list those controls, on its tab or in a collapsible group by the rules in `docs/modules/README.md` (no Advanced controls toggle, decision 29), with when each shows and its quads, and darktable's presets; add or update the module's entry and page there in the same change. A choice lists the options darktable lists for the photo, those the port does not take drawn disabled (decisions 29 and 30: the definition holds every option darktable lists on some photo, `Module::options` those it lists on this one, and the module's table holds in an invariant row how an option another photo's edit holds renders, as darktable's darkroom renders it); a control whose parameter is not ported is drawn disabled. Its sliders are darktable's, as `gui_init` sets them: the hard range as the control's, the soft range as the track's, the factor and offset, the digits and the step, recorded in the module's table and held by `testing::slider_differences` in its source (decision 30; `tool-bindings`, rule 1). Where darktable's `gui_changed` moves a slider's range with other controls, read where it does and what it does to the value, and give the range through `Module::range`, the definition's range the widest any values give (decision 30: AgX's pivot over the input range). What follows from mirroring darktable is the architect's to decide, not the user's; bring the user only a deviation from that rule, scope darktable does not cover, or a blocker.

## Step 1: Write the spec

1. Get the reference source. The local clone may only have master, so fetch the tag and read files from it. `upstream` below is the remote that points at github.com/darktable-org/darktable; a fresh clone calls it `origin` (`git -C "$DARKTABLE_SRC" remote -v`).

   ```sh
   DT_TAG=release-$(sed -n 's/^pub const REFERENCE_VERSION: &str = "\(.*\)";$/\1/p' crates/golden/src/darktable.rs)   # the reference release, from the repository root
   git -C "$DARKTABLE_SRC" fetch upstream tag "$DT_TAG" --no-tags
   git -C "$DARKTABLE_SRC" rev-parse --short "$DT_TAG^{commit}"   # the commit, not the tag object
   git -C "$DARKTABLE_SRC" show "$DT_TAG":src/iop/<file>.c
   ```

2. Copy `templates/module-spec.md` to `docs/ports/<module>.md`.
3. Read the module's source using `references/darktable-source-map.md` as a guide to where things live, and fill in every section.
4. Mark each place where Apertrust deliberately differs from darktable under **Deliberate differences**, with the reason and its size. Typical reasons: fp64 maths redesigned for fp32, a branch removed because Slang's backward pass recomputes it, a parameter fixed to a default because it has no editing meaning. These stay within the case's tolerance, and are no departures. **A port departs from what darktable-cli exports only where a difference is agreed** (decision 63): darktable's behaviour then stays behind a setting only the golden harness reaches, never in the schema, an edit or a module (a typed setting outside the schema that only `ports.rs` sets), so the golden cases check everything else against darktable, and the spec states the difference's size, measured. How smaller views compute the operation follows principle 2 (the same processing at their scale), not darktable's preview pipe, and is no departure, a branch darktable takes on a length scaled to the pipe included, which follows the full-resolution length (decision 63; Step 2, scale-aware neighbourhoods). Where darktable's own result is not reproducible (it depends on how its binary rounds, or a solve fails), the spec records the choice and its size as a deliberate difference. Ask before any departure; it is the user's call.
5. For a large module (more than one algorithm, or more than about 1,500 lines of C), stop after the spec and ask the user to review it before writing kernels. A wrong spec is cheap to fix; a wrong kernel is not.

What matters most when reading darktable's source:

- **The parameter struct and its introspection comments** (`$MIN`, `$MAX`, `$DEFAULT`, `$DESCRIPTION`). These become the parameter schema.
- **`legacy_params`**: every older parameter version and how it migrates. The spec records the whole history; `ports.rs` migrates the versions the golden cases contain, exactly as darktable does (darktable's tests use old ones: `agx-default` is AgX's version 4). The import of darktable's edits will need every version darktable can store, each tested against darktable's own values (decision 51, planned).
- **`commit_params`**: how user parameters turn into processing data. Often this is where the real maths starts, and it becomes the CPU-side `prepare`.
- **`process`** (CPU) and **`process_cl`** with its OpenCL kernels. Treat the **CPU path as the truth**; note any place where the OpenCL kernel differs.
- **`modify_roi_in` / `modify_roi_out`**, `tiling_callback`, and any use of `roi->scale` or `piece->iscale`: neighbourhood size and scale dependence, which decide tiling overlap and preview behaviour, and any branch taken on a length scaled by them, such as the colour equalizer's blur in place where a grid is not downsampled, which the spec names (decision 15). `tiling_callback`'s overlap becomes the operation's reach (`Operation::reach`, decision 13), from the same parameters and scale.
- **`dt_ioppr_get_pipe_output_profile_info`** (filmic rgb's gamut mapping) is `ImageContext::output_profile`, the pipe's output profile as matrices, `None` meaning the working profile (decision 26); `dt_ioppr_get_export_profile_type` (AgX's "export profile") is the edit's, the same until an export gains a profile of its own. A case that depends on it sets its output profile and compares after colorout (`golden-tests`).
- **The data files and the image fields it reads**: darktable's data files (its noise profiles, `noiseprofiles.json`) ship verbatim at darktable's path in Apertrust's top-level `data/`, embedded by the one crate that parses it (decisions 24 and 45); `dt_image_t`'s `camera_maker`, `camera_model`, `camera_alias` and `exif_iso` are the image context's `make`, `model`, `alias` and `iso`, in darktable's spelling (decision 27), darktable's white balance presets for the camera its `white_balance_presets` (decision 27, planned), and its `exif_correction_type` and `exif_correction_data` its `lens_correction` (decision 25; Fujifilm built, the other types to come).
- **The working colour space** the module expects and returns (darktable's default is linear Rec2020).

## Step 2: Write the kernel and its setup

The `slang-kernels` skill has the details: the interface, uniform layout, the build and validation commands, and how to debug a failing gradient check. The conventions that shape a port:

- **fp32 only.** Any `double` maths in darktable is redesigned for fp32, not translated line by line; note it in the spec.
- **No reliance on NaN or infinity checks.** WGSL implementations may assume they never occur. Sanitise inputs at operation boundaries instead.
- **No write to a local at a run-time index.** darktable's `sum[c] += v` over a CFA colour becomes `sum = add_at(sum, c, v)`, and `color[f] = v` becomes `color = set_at(color, f, v)` (`import components;`), because FXC, the Direct3D 12 compiler the engine pins, cannot compile the indexed write (decision 10; `slang-kernels` has what counts).
- **Storage buffers by default.** Textures only where hardware sampling helps (resampling, lens distortion, rotation); geometry interpolates in its kernel with darktable's interpolators, never by hardware filtering, whose precision differs between GPUs (decision 16).
- **Keep data on the GPU.** No readback between modules.
- **Separate the parts** (decision 8): a parameter struct, any once-per-image setup, and a pure per-pixel function of the pixel and those parameters, so per-pixel modules can later be fused into one pass.
- **Differentiable.** Mark the per-pixel function `[Differentiable]`, export `<module>_backward` (reverse mode) and `<module>_forward_diff` (forward mode) as the existing kernels do, and document their parameter order. The raw stage is the exception (decision 21): its parameters are never optimised and its data are mosaics, so its kernels set `derivatives: false` and the manifest `differentiable: false`, and export neither. Avoid unnecessary hard clamps, thresholds and branches; where darktable needs one, note in the spec what smooth approximation the optimisation path would use.
- **Two Slang derivative traps** (the kernel spike): use `pow0` from the colour library, never `pow`, whose built-in derivative is zero below 1e-6; and never let a branch decide which table entries a differentiable function reads, because the backward pass recomputes the condition and can read an entry the forward pass never saved.
- **Scale-aware neighbourhoods.** Radii given in image pixels scale with the processing resolution exactly as darktable scales them with `roi->scale`, or the preview and the export differ. Every pipe scales its lengths as darktable's export at that size does, never its darkroom or preview shortcuts (non-local means keeps K in the viewport, decision 15). Where darktable rounds a scaled length to an integer that need not be one, compute it at full resolution as darktable does and scale that, unrounded, so every pipe's length follows the export's (decision 15; the tone equalizer's EIGF radius). A size darktable derives from the scaled length (a grid's downsampling, the guided filter's grid radius) keeps darktable's derivation and rounding at the pipe's scale. **An iterated box mean matches its variance** (decision 63): where darktable applies one box mean of radius R N times (`dt_box_mean` with N iterations, as bloom and soften do), take the passes' radii at the pipe's scale from `apertrust_color::box_filter`, r and r + 1 so that Σ r_i (r_i + 1) is nearest N s² R (R + 1), every pass R at scale 1; one radius rounded to the nearest makes the blur up to 27 % too wide. A single box mean keeps the nearest radius. **A branch darktable takes on a scaled length follows the full-resolution length** (decision 15): where a scaled length crossing a threshold switches between computations that render different images at the same lengths, every pipe takes the branch the export takes at scale 1, as darktable-cli's export does at any size, its high-quality processing running the pipe at full resolution; the colour equalizer blurs in place only where the export's σ is under 3.5 pixels, its grid sized at the pipe's scale. The test: run both sides at the same lengths; if they differ, it is a branch. A guard that only keeps a computation defined at a small size (a grid at least a pixel wide) stays at the pipe's scale.
- **Whole-image passes** (`PassKind::Reduction` in the code, `PassKind::WholeImage` its planned name; decision 15): a pass that needs the whole image before the operation's later passes run, a statistic or a grid, writes its result into scratch, whatever its size, and runs over the whole image at the pipe's scale in every pipe, never a visible region. After demosaic they form runs, each the passes that read the operation's input and then those that read only scratch, and each run costs a tiled export a round of tiles, taken only when the operation opts in (`Operation::tiles_whole_image_passes`: every input-reading pass writes only the scratch its tile owns, so a pass reading across tile edges, as local contrast's reduce does, rules it out) and is one run; otherwise everything up to it runs whole (decision 15). Keep as few runs as you can: where darktable keeps a full-resolution intermediate between iterations, write it once from the input into scratch laid out as an image, which its passes are to bind in row strips (planned, decision 15), rather than reading the input again in each iteration (the tone equalizer's EIGF). Give the whole-image passes a uniform block of their own holding only what they read, never a parameter only the later passes use (the tone equalizer's band curve), so changing that parameter leaves their key unchanged and its drag runs none of them in the viewport (decision 15, built), and test that it does: their bytes in the setup's tests, the drag in the engine's `viewport.rs`, as the tone equalizer's bands and haze removal's strength are. None of them writes the output, and a pass after them writes only scratch they do not write. Lay out grid buffers as float2 halves, never float4: a grid's line passes cannot run in strips, so each buffer must fit one binding. A grid read by a later pass is sampled at the pixel's absolute position, and its geometry is the whole image's at the pipe's scale, never a tile's. A port with whole-image passes after demosaic also meets the viewport's target against the export (`docs/engine.md`, Pipes), on the per-pixel gap stated per step (decision 15): the baseline holds every value a pixel reads from other pixels (a blur, a filter's coefficients, a grid, a statistic, a gradient) at the export's, downscaled by the viewport's box filter, and computes every value from the pixel's own and those at the viewport's scale, whichever pass computes it, through a setting only the tests reach; the operation's own mode without its filtering is the baseline only where it drops nothing else. Measure it on the golden cases' image with the port, and on decision 15's four corpus renders before the operation's module ships.
- **Spatial operations after demosaic** (decision 13): declare the reach through `Operation::reach(params, image)`, at the pipe's scale, all the operation's passes together, computed by the same setup `prepare` uses. The kernel indexes its input from absolute coordinates less its input's origin, treats only the image's edges as edges (the header's full size, never the region's) and computes each output pixel in an order fixed relative to that pixel, never sums slid across a workgroup, so its tiles equal the untiled export wherever a tile or workgroup starts. Until the engine's regions are built, its export runs whole up to it; the port's tiled test comes with them.
- **Shared helpers go where their users are** (decision 65): darktable's helpers from `src/common/` (filters, resampling) stay in the port, in a Slang module of their own beside the kernel, in a folder `tools/build-kernels.sh` does not compile as a kernel, with their Rust references in a module of their own, until a second port that calls them is scheduled on the board; then they go into an existing shared crate, `apertrust-color` for image maths (its `slang/` is on every kernel's import path) or `apertrust-plugin` for the pass interface, written for both users from the start and naming the scheduled port in their documentation, as bloom's box mean is for soften. A new crate waits for a second port that uses it: a crate with one user protects no boundary (decision 65). If the scheduled port is dropped, the helper moves back.
- **Raw-stage passes before demosaic run in row strips** where the mosaic is larger than the GPU binds at once (decision 14): each pass that reads or writes the mosaic sets `Pass::strips`, and its kernel takes its first row from the header's origin and indexes the whole mosaic less the header's `input_base` and `output_base`; a statistic's per-workgroup pass keeps whole workgroup rows and writes its result at its index in the whole image (`slang-kernels`, Row strips). Demosaic runs whole or in tiles of its own and sets none. The port's tests then cover a GPU opened to bind less (`GpuOptions::max_storage_binding`), as `crates/engine/tests/highlights.rs` does.
- **Licence header**: the GPLv3 header from AGENTS.md, plus darktable's copyright line with the years from the source file you port, e.g. `Copyright (C) 2009-2026  darktable developers (ported from src/iop/exposure.c)`.

Then:

1. Run `tools/build-kernels.sh` and commit the generated WGSL next to the source, so diffs show what changes on the GPU.
2. Add the crate to the workspace dependencies in the root `Cargo.toml` and to `apertrust-operations`, and its `KERNEL` to `KERNELS`. `cargo test -p apertrust-operations -p apertrust-engine --test naga` validates every operation's kernel with naga and checks that it has `main`, and `<module>_backward` and `<module>_forward_diff` when the kernel declares `derivatives`; the engine's test checks every kernel, the operations' included, for writes at a run-time index; another test checks that each operation's manifest agrees with its kernel.
3. Write the CPU-side setup (`prepare`) from `commit_params`, returning the kernel's parameter bytes and tables. Return `NotPorted` for settings the port does not cover yet.

## Step 3: Add the golden case and pass the checks

The harness (`apertrust-golden`; the `golden-tests` skill covers it in depth) renders darktable's input and expected output for one module as linear Rec2020 PFM, runs our kernel on the input, and compares with CIEDE2000.

1. **Pick a case.** Start from darktable's integration tests (`$APERTRUST_TEST_IMAGES/../<NNNN>-<name>/<name>.xmp`), which exercise the module on a known image. Copy the sidecar to `crates/golden/cases/<case>.xmp`. Add a `Case` in `cases.rs`: `disable` later modules that would change the result (such as `filmicrgb`), and if the test applies the module through a drawn mask, set `unmask_like` to an unmasked operation so the case covers the whole image. A sidecar can be edited to add a case for a mode the tests lack, as `blurs-motion` was.
2. **Render the references**: `cargo run --release -p apertrust-golden -- render <case>`. Check the reported module effect is well above zero; otherwise the case isolates nothing.
3. **Translate the parameters** in `ports.rs`: decode darktable's params (every version the case can contain), and return `KernelInputs` from `kernel_inputs`; for the gradient check, add `gradient_parameters` and `perturbed_inputs`. An operation of several passes, or with scratch buffers, returns schema values instead from `plan_values`, with `perturbed_values` for the gradient check and `plan_context` for the image context, the case raw's camera included, as colour balance rgb's case builds them, and its cases run as a one-instance plan of the engine; its derivatives are those of the pass that writes its output, which the engine dispatches over the scratch the forward render left (decision 15; `golden-tests`).
4. **Run it**: `cargo run --release -p apertrust-golden -- run <case> [--heatmaps DIR]`. It passes within the case's mean and max ΔE2000 tolerance, `Tolerance::DARKTABLE` unless the spec argues otherwise.
5. **Check the gradients**: `cargo run --release -p apertrust-golden -- gradient <case>` and `-- gradient <case> --synthetic`. Reverse mode must match finite differences within 1% and agree with forward mode per pixel; use `--explain` to see where a gap sits. A gap you cannot close goes into the spec, understood.
6. **Invariants**: outputs stay finite for extreme inputs (very bright, zero, negative). A module that is off being a no-op is the owning module's test (`tool-bindings`). An operation an unedited photo does not run is planned only while a module sets it (decision 28), or while its switched module is on: a module darktable leaves off on a new photo is switched, off until a control changes, then on with darktable's defaults, its reset turning it off (decision 32), whether or not a setting of its operation is an identity. So the spec gives darktable's defaults for a new instance (`reload_defaults` where they follow the photo), which the module starts from, says whether the operation at them is an identity, and on which pixels it is not, for the module's first-step row, and says "What is an identity: none" where no setting is one (bloom blooms at strength 0; denoise's strength cannot reach 0).

Never change a case or its tolerance to make a port pass. If a reference or tolerance must change, say why and get the user's agreement.

## Step 4: Record provenance and finish

1. Put the provenance in the spec's header: darktable, the reference release, the commit from step 1, and the source files; the manifest's `Provenance` records the release number.
2. Record the results in the spec: ΔE2000 mean and max per case with the GPU used, and the gradient check.
3. Set the spec's status: **ported** (checks pass) or **verified** (checks pass on GPUs from at least two vendors).
4. If the port changed anything architectural (the kernel interface, a convention, the pipeline order), record it with the `decision-log` skill, after the user agrees.
5. Summarise for the user: what was ported, ΔE and gradient results per case, deliberate differences, and anything left open. The user commits; draft the commit message if asked, in `/draft-commit`'s style.

## Following an upstream darktable change

The reference is darktable's latest stable release (decision 3). When a newer release comes out, moving to it is its own piece of work, in AGENTS.md's steps. For each ported module:

1. Diff the module between the two tags: `git -C "$DARKTABLE_SRC" diff $DT_TAG <new-tag> -- src/iop/<file>.c data/kernels/<file>.cl`.
2. Classify each change: bug fix to follow, behaviour change to evaluate, or refactor to ignore.
3. Update the spec first, then the kernel, then re-render the references with the new darktable-cli and rerun the checks.
4. Update the provenance: the spec's header and the manifest's `Provenance`.

## Common pitfalls

- **Hidden dependencies on other modules.** Some modules assume an earlier module ran (raw data still mosaiced, a particular working space, white balance applied). Write these assumptions into the spec's pipeline section, and disable later modules in the case.
- **Scale-dependent parameters.** A blur radius that looks right at full resolution is wrong in the preview unless it scales.
- **The reach** (`Operation::reach`, by default the manifest's radius) is the border a tile needs: too small, and a tiled export differs from the untiled one at tile edges (`crates/engine/tests/tiles.rs`, decision 13).
- **Parameter versions.** A case whose sidecar holds an older version needs `ports.rs` to migrate it exactly as `legacy_params` does, or our kernel and darktable render different settings.
- **Random numbers.** darktable's noise (vignette's dithering) can depend on its thread count and tiles, and cannot be matched pixel for pixel: decide what the port covers, and record the measured gap. Other noise is deterministic (grain's simplex noise on the position): port it exactly.
- **darktable's `-ffast-math`.** Its release builds compile with `-ffast-math` (`src/CMakeLists.txt`), which turns a division by a constant into a multiplication: grain's `8 * scale / 100` is `scale * 0.08f`, one ulp off the correctly rounded quotient. Where a value magnifies such a last bit (grain's offset, 3e5 noise cells), follow the build's arithmetic, and confirm it with a case whose settings tell the two forms apart.
- **A kink on the synthetic sweep.** When forward and reverse mode agree but finite differences miss in one column or row of the sweep, an edge of a position-dependent kernel lies on it (vignette at a near-rectangular shape): check that parameter on settings chosen by a float64 emulation of the check under small moves of each setting.
- **Mask and alpha handling.** darktable blends a module's output through masks. Apertrust's layers blend in the engine, so a kernel never blends its own output, and cases cover the whole image.
- **OpenCL differences.** Where darktable's OpenCL kernel and CPU code disagree, follow the CPU code and note the difference.
- **Spatial modules.** No module exports derivatives with respect to its input image yet; for a gather, reverse mode is a scatter WGSL cannot do without float atomics (the kernel spike). Note in the spec what the module would need.
