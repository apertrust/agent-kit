# New plugin

Every operation, built-in or third-party, is a native plugin behind one interface (`docs/plugins.md`; decisions 4 and 20). An operation is one engine algorithm: darktable's iop without its GUI. Modules, what the user sees, bind to operations' parameters (`tool-bindings`). darktable modules are never loaded; a darktable port is an operation whose maths comes from darktable's source (the `port-module` skill).

**Status:** the layout is decided (decision 20, below), and operation crates exist, each with its Slang source, generated WGSL, setup and `KERNEL`. Every one implements the `Operation` trait (`apertrust-plugin`) and is in `OPERATIONS`, in darktable's v5.0 order (decision 22). rawprepare, temperature, highlights, demosaic, colorin, exposure, channelmixerrgb (color calibration), AgX and colorout have `default_enabled` on, so the engine's pipeline runs them on every photo. toneequal, colorbalancergb, rgbcurve, rgblevels, bilat (local contrast), bloom, soften, colorequal, primaries, hazeremoval, grain, vignette, sigmoid and filmicrgb have it off, so the session plans them only while a module sets them, or, for a switched module, while it is on (decisions 28 and 32). Use `crates/op/agx/src/lib.rs` as the model: its manifest, its schema of darktable's field names with their ranges and defaults, `prepare` calling the setup, and the tests that tie the schema's defaults to darktable's.

## What a plugin is

| Part | Purpose |
| --- | --- |
| Manifest | ID, version, domain (scene or display), slot (a stage and an order number, darktable's where Apertrust keeps darktable's place; decision 22), layer support, differentiable flag, the neighbourhood radius at full resolution, a fixed reach and the default of `Operation::reach`: the border a tile needs on every side for its output to equal the untiled one bit for bit (decision 13), and `default_enabled`: whether an unedited photo runs it (decision 28) |
| Parameter schema | Engine parameters with ranges, units and meaning; versioned, with migrations |
| Kernels | Slang source, with one entry point per pass and, outside the raw stage and for an operation with a continuous parameter, the derivative entry points (decisions 11 and 21; none for `flip`, `colorin` or `colorout`), and its generated WGSL (`slang-kernels`), plus an optional CPU reference for tests |
| Setup | `prepare`: from the parameters and the image's context to uniforms and tables, as darktable's `commit_params` does |
| Tests | Golden cases and invariant tests (`golden-tests`) |
| Provenance | The darktable module, its source files and the release commit it was ported from |

The engine builds the pipeline from manifests: the operations an unedited photo runs, and every other operation only while a module's binding sets one of its parameters (decision 28). Modules bind their controls to operation parameters, the UI builds module panels from module definitions, and MCP exposes the modules. A plugin has no UI of its own: a module can drive several operations, so module definitions live in `apertrust-modules` (`tool-bindings`). Everything a module or a client needs about an operation must be in these parts, as data, never in client code.

## Layout (decision 20)

```text
crates/op/agx/      apertrust-op-agx
  slang/agx.slang           one entry point per pass, plus agx_backward and agx_forward_diff
  generated/agx.wgsl        committed, validated with naga
  src/setup.rs              prepare(): darktable's commit_params
  src/lib.rs                manifest, schema and its versions, provenance, impl Operation
```

- **`apertrust-plugin`** holds the `Operation` trait (`manifest`, `schema`, `prepare`) and its types, as plain data and without wgpu, so a declarative package can implement it later.
- **`apertrust-operations`** lists the built-in operations explicitly. The engine depends only on `apertrust-plugin`; the binaries hand it the list.
- **`apertrust-color`** holds the colour maths operations share: `color.slang` for kernels, `color.rs` for setups.
- **What `prepare` receives and returns** (decision 21): the image description carries the format and size and, like darktable's buffer descriptor, the image's position on the sensor, each channel's saturation level, the white balance applied and whether colorin must still correct it; an operation that changes them (rawprepare, temperature, demosaic, colorin) says so in its output. Scratch buffers are sized in bytes, and a pass may run over a size of its own (`Pass::size`), as demosaic's do over its input.
- **Parameters cross the interface as data** (names mapped to numbers, whole numbers, choices or booleans, checked against the schema; decision 21; an array's elements take an `_<index>` suffix); each built-in operation converts them into its own typed settings.
- **The reach** (decision 13): an operation whose neighbourhood depends on its parameters or the scale overrides `Operation::reach(params, image)`, the pixels beyond its output region at the pipe's scale that its output reads, all its passes together, as darktable's `tiling_callback` gives its overlap (non-local means' `P + K_scattered`); the default is the manifest's radius times the scale, rounded up. Compute it in the same setup function `prepare` uses (non-local means' offset table), so the two never disagree. The planner calls it before `prepare` to work regions backward: export tiles after demosaic grow by it, demosaic writing the grown region, and `prepare` is told its output region and sees its input's through `ImageDesc`'s extent and origin (planned, with the regions; until then an operation after demosaic with a reach above 0 runs whole with everything before it in an export). Where no tile takes the reach, the operations up to it run whole, as darktable's tiling gives up. A pass's `PassKind::Spatial` radius is its own reach, informational.
- **Passes** are per-pixel (the engine can fuse them, unless they bind scratch: a per-pixel pass may write scratch for a later pass and is then never fused, with no kind of its own, decision 13), spatial (with a radius) or whole-image (`PassKind::Reduction` in the code, `PassKind::WholeImage` its planned name; decision 15): every pass that computes a result from the whole image at the pipe's scale before the operation's later passes run, a statistic (from preparing its input to the partial results per workgroup and their combination; highlights' inpaint opposed) or a grid (the tone equalizer's mask), writing into the operation's scratch buffers, which its later passes bind, with no readback. The result may be any size: it is its scratch buffers', counted in the plan's memory. Whole-image passes cover the whole image in every pipe, never a visible region, and their result stays the whole image's even where they run in row strips (below). That whole image is the input's stage at the pipe's scale, after a geometry that geometry's output (decision 16): take it from `ImageContext::whole_image(input)`, which returns the stage at the pipe's scale, `ImageDesc::scaled_extent`, which the planner sets for every RGBA image in every pipe (decision 15): the stage's `extent` at full resolution, the fitted size after the viewport's downscale, and after an export's resample without high quality its output, the export's size; a tile's input is the part of it at its `origin`, the pass header's origin placing each pixel in the scratch. A test that builds a tile's `ImageDesc` by hand sets `scaled_extent` with `extent` and `origin`. Never from the image context's size and region, nor from a scale of 1, which a viewport whose scale rounds back to 1 also has, nor from the extent times the scale, which can round a pixel off darktable's export size. A whole-image pass before a geometry that keeps part of its stage (crop's window) is refused until crop is built. In the viewport their result is keyed apart from the operation's other passes, on their input's key and their own bytes, and kept in their scratch while the key holds, across a rebuild too, so changing only the later passes reruns none of them (decision 15, built: `PlannedOperation::whole_image`; an export plans them out of its rounds instead). For that, their uniforms and tables are a block of their own holding only what they read, never a parameter only the later passes use (highlight reconstruction's passes share one, rightly, since all its parameters feed its statistic), and a test holds that changing such a parameter leaves their bytes unchanged; the passes up to the last whole-image one count as its, any per-pixel one between them included, none of them may write the output (the planner then keys nothing), and a pass after them, a per-pixel one writing scratch for a later pass among them (decision 13), may write only scratch they do not write. The engine's `viewport.rs` checks a drag of such a parameter, as the tone equalizer's bands and haze removal's strength. After demosaic they form runs, each the passes that read the operation's input and then those that read only scratch, which the bindings tell apart. An export gives them a first round of tiles only when the operation opts in through `Operation::tiles_whole_image_passes(params)`, every input-reading pass writing only the scratch its tile owns, and its passes are one run; otherwise everything up to and including it runs whole (decision 15). An operation whose estimate is not scale-invariant opts in through `Operation::whole_image_at_full_resolution(params)` to have its whole-image results computed at full resolution in the viewport too (decision 15; haze removal), and in an export at a size without high quality, where the resample then comes after it (decision 15, planned), so the operation runs there as in the full-size export: as built, where the viewport is untiled and the operation comes straight after its downscale, `prepare` then gets `ImageContext::full_resolution`, the image the downscale read, which its whole-image passes bind as `Resource::FullResolution` and run over at full resolution, and the operation itself downscales what its later passes read per pixel to the viewport's size with the viewport box filter's integer footprints and f32 sums, calling `box_downscale.slang`'s `footprint_mean` as the engine's downscale does (haze removal's `plane_downscale`); elsewhere `full_resolution` is `None` and it prepares as any operation does. Built (decision 15; `WholeImage::full_resolution`): the passes up to the last that binds `Resource::FullResolution` are its full-resolution part, keyed on that image's key at scale 1 so a resize keeps them, their pass header saying scale 1 and origin 0, and its later whole-image passes, the downscale among them, are kept with the whole on the viewport's key; so put every pass that depends on the viewport's size after the last that binds the full-resolution image, and in the full-resolution part bind neither the input nor the output and give every pass a size of its own (`Pass::size`), since one without runs over the viewport's output (otherwise the planner keeps one part, rerun on a resize), and read of the pass header only the dispatch size. Skipping the part is exact only if no later pass writes scratch the part writes, which the planner cannot check, a binding not saying whether a pass writes it: write the viewport's planes into scratch of their own, as haze removal's `plane_downscale` does. As built, an export takes that round only for an operation whose whole-image passes are one run and which overrides `Operation::tiles_whole_image_passes` to say that each pass reading the input writes only the part of its scratch the tile owns, as the tone equalizer's grid samples are computed by the tile holding their north-west node; by default, `false`, the export runs the operation and every one before it over the whole image. A grid's buffers are float2 halves, since its line passes cannot run in strips and each buffer must fit one binding; a full-resolution intermediate is scratch laid out as an image, to be bound in row strips like one (planned, decision 15: until then an iterated tone equalizer mask above about 33 MP is refused on lavapipe). In a tiled export the whole-image scratch the export holds is left out when the tiles are sized, and logged under `-d memory` where the total exceeds the budget (decision 15), so a large result (denoise's wavelets, 2.9 GB at 61 MP) never leaves the export without tiles. An operation's derivative entry points belong to the pass that writes its output, and the engine dispatches them with that pass's bindings over the scratch its forward passes left; declare a gradient slot only for a parameter that no whole-image pass reads, or that a restructure makes exact (decision 11).
- **Readouts** (decision 19, planned; `docs/engine.md`, Readouts): what an operation measures of the photo for its module's panel, as darktable's GUI computes from its preview pipe (the tone equalizer's mask histogram; RGB levels' and RGB curve's input histograms). List each id in `Manifest::readouts`; return, from `prepare`, a `ReadoutPass` for each in `Prepared::readouts`, never among `passes`: one pass of the kernel binding what its passes bind (the input, scratch the whole-image passes left) and its counts buffer as `Resource::Readout`, writing nothing else, with uniforms holding only what it reads, so a parameter only the other passes use leaves its key alone; and decode the counts on the CPU in `Operation::readout(id, words)` into `ReadoutValue` (a `Histogram`), restating darktable's GUI arithmetic exactly, counts in and plain data out, never a pixel. The engine runs it in the viewport alone, while a client asks and its key has changed; no export, tile, golden case, fusion or derivative sees it, so it has no derivative entry points. Count it as `slang-kernels`' "A count" says. Test the decode against a restatement of darktable's function, and the pass against a CPU count of the same values kept clear of the bins' edges.
- **Geometry** (decision 16; the engine's side built, the first operation with orientation): an operation that moves pixels (orientation, crop, rotate and perspective, lens correction) returns a `Geometry` from `Operation::geometry`: its module's `modify_roi_out` (`extent`), `modify_roi_in` (`input_region`, the interpolator's margin included, given its input's `Extent`, its size at full resolution and at the pipe's scale) and `distort_transform` and `distort_backtransform` (`forward`, `backward`), ported in f32 so sizes match darktable's, its kernel evaluating the same map per pixel and a test holding the two together on a grid. `prepare` gets its input region in its `ImageDesc` (`extent` and `origin`) and returns an image of its output region's size, which the planner checks and places; it is not told its output region yet, which the regions settle (decisions 13 and 16), so until then a kernel works from its own input and output regions, as darktable's flip turns its input buffer. It interpolates with darktable's warp interpolators in the kernel, never by hardware filtering; its passes take no strips, which the planner refuses; a geometry that only translates its input (crop) returns no passes (`docs/engine.md`, Geometry, As built). A warp clamps its sample positions to, and mirrors its taps at, the bounds `prepare` is told: `input_region` of the untiled output requirement at the pipe's scale, darktable's `roi_in` of an untiled export, the same in every tile; its region for a tile holds every tap of the tile's pixels so clamped, inside the bounds, which darktable's `modify_roi_in` of the tile alone can miss by one tap (decision 25, planned).
- **Row strips** (decision 14): where an image is larger than the GPU binds at once (lavapipe's 128 MiB), a pass that sets `Pass::strips` runs once per band of rows, binding a window of each image; one without strips needs its images whole, and a plan that would bind more does not fit. A raw-stage pass before demosaic that reads or writes the mosaic sets it, with the rows of the image a row of its invocations covers, the halo it reads and, for a pass writing a partial result per workgroup, a granularity of 16; its kernel follows `slang-kernels`, Row strips. Scratch buffers stay whole. Demosaic, though in the raw stage, and every pass after it run whole or in tiles of their own instead and set none.
- **Images, bindings and scratch** (decision 21): `prepare` receives the image it gets and returns the one it produces (size and format: 16-bit mosaic, f32 mosaic or RGBA). Each pass lists exactly what it binds, by convention input 0, output 1, uniforms 2 (a 48-byte pass header, then the operation's parameters), tables 3 to 7, scratch 10 up; `Pass::per_pixel` keeps the usual layout. An operation's passes share the scratch buffers it asks for, sized in bytes (decision 21).
- **Defaults from the image**: override `defaults(image)` where darktable's `reload_defaults` reads the image (crop, levels, as-shot white balance, the CFA, exposure bias, the noise profile); the image context carries the camera's metadata and its identity as darktable's names mean it: `make`, `model` (darktable's `camera_model`, an alias resolved to its main camera), `alias` (`camera_alias`, the name the file's camera has) and `iso` (`exif_iso`, 0 if unrecorded) (decision 24), each in darktable's spelling where darktable's differs from rawler's (decision 27), the camera's white balance presets from darktable's `wb_presets.json`, `white_balance_presets` (decision 27, planned), and the lens corrections the raw carries, `lens_correction`, darktable's `exif_correction_type` and `exif_correction_data` as darktable stores them, every table computed in the operation (decision 25; Fujifilm built, the other types to come). Look darktable's data up by `model`, the canonical name, as darktable does, trying `alias` first where darktable keys an entry by a name rawler holds as an alias.
- **The output profile** (decision 26): an operation that gamut-maps against the output profile, as darktable's filmic rgb reads `dt_ioppr_get_pipe_output_profile_info`, reads `ImageContext::output_profile` in `prepare`, matrices to and from XYZ D50, `None` meaning the working profile; never in `defaults` or a binding. The operation that writes the output, colorout, reports it through `Operation::output_profile(params)` (default `None`), which the planner asks of every instance before any `prepare`. The engine never reads an operation's parameters by id.
- **darktable's data files** (decisions 24 and 45): a port that needs one of darktable's data files (its noise profiles, `noiseprofiles.json`) ships it verbatim at darktable's path in the top-level `data/`, with its first consumer, embedded with `include_str!` by the one crate that parses it and parsed once on first use, its release, blob, size and checksum in `data/README.md`, a test holding the checksum and the file named in CREDITS.md's darktable paragraph; data the module needs too reaches both through a crate both reach or the image context, since `apertrust-modules` depends on no operation crate, as White balance's camera presets reach temperature's defaults and the module through `Camera::white_balance_presets`, which `apertrust-raw` fills (decision 27); JSON through serde_json. The image context's names are darktable's spellings already: `apertrust-raw` holds the short hand-written list of darktable's names that differ from rawler's and applies it to `make`, `model` and `alias` (decision 27), so a lookup tries `alias`, then `model`, with no list of its own.
- **Slots**: the stage whose data the operation reads (raw, camera RGB, working space, display or output), then its order number; demosaic and the tone mapper are operations within a stage (decision 21). The order of every built-in operation is `crates/operations/order.md`'s table (decision 22), and in the first pass every operation keeps darktable's place (decision 22): an operation keeps darktable's v5.0 number where it keeps darktable's place, its position in darktable's list, and otherwise takes a number between its new neighbours in that list, its spec saying why, as it does where darktable's number disagrees with its position (lut3d, numbered 36, is listed after filmic rgb); no two operations share a slot, and the numbers rise with the stages, so the number alone gives the order.
- The port spec stays in `docs/ports/<id>.md` and the golden cases in `apertrust-golden`.

## How plugins load

1. **Built-in modules are compile-time plugins**: each is its own Rust crate implementing the plugin interface and registering at build time. Modular from day one, type-safe, no runtime loading.
2. **Third-party plugins come later as declarative packages**: manifest, schema and WGSL kernels as data, with any CPU-side logic (lookup tables, statistics for Auto) as a sandboxed WebAssembly component, and a module definition that binds the package's parameters.
3. **No native shared-library plugins**: Rust has no stable ABI, packaging would be per platform, and a faulty plugin could crash the app.

Design the built-in interface so a declarative package can satisfy it later: data where possible, code only where it must be.

## Rules the engine enforces

- **A plugin declares its slot; it cannot reorder the pipeline.** `crates/operations/tests/order.rs` holds the two rules (unique, rising with the stages) and every built-in operation to `crates/operations/order.md`'s table, which a new operation joins in the same change. A third-party slot another operation has, or a number out of step with its stage, will be refused at load (decision 22).
- **Kernels keep data on the GPU.** No readback between modules; only a readout's counts are read back, by the session, for a module's panel (decision 19).
- **Kernels avoid what Direct3D 12's compiler rejects.** No kernel writes a local vector component or array element at a run-time index, which FXC, the Direct3D 12 compiler the engine pins, fails or may fail to compile (decision 10; `slang-kernels`). The engine's naga test checks the built-in kernels on every machine; when third-party plugins arrive, the engine runs the same check on their kernels at load and refuses a kernel that fails it.
- **Schema versions and migrations are mandatory**, so old edits keep their look. A new schema version comes with a migration from the previous one, and an invariant test that the migrated edit renders as before. It is needed when a parameter an edit can store (one no module owns yet, of an operation an unedited photo runs) is removed or renamed, or has a choice removed or renamed, its range narrowed, or its default or meaning changed. A parameter a module owns is the module's version's concern (`tool-bindings`).
  - A new parameter, a new choice or a wider range needs none (decision 48): an older build that finds one in an edit opens the photo for viewing only (`docs/engine.md`, What a save may drop).
  - A committed record of the parameters an edit can store, held by a test (planned, decision 48): a removal or change at the recorded version fails until the version rises, and an addition until the record is blessed, as `tool-bindings` describes for modules. A parameter a module takes leaves the record with no raise, since the reader drops an owned parameter as an older build's.
  - An operation removed or renamed joins a list of retired operations in `apertrust-operations`, made with the first, so edits holding its parameters stay editable.
- **Only differentiable plugins take part in optimisation** (reference matching, agent-driven edits). Built-in modules are differentiable unless there is a recorded reason.
- **One owning module per parameter**, across plugins too: depth comes from inside the owning module, its own tabs and collapsible groups (decisions 2 and 29), never from a second module (AGENTS.md; `docs/modules/README.md`). A test refuses a built-in module that owns a parameter another module owns, or one that does not exist; at run time the session reports such a module as failed and leaves it out. The operation-level `Set` is refused on an owned parameter and on any parameter of an operation an unedited photo does not run (decision 28).

## Scaffolding a plugin

A new operation needs, in order:

1. **The manifest**, with the slot: the stage it reads, and its number in darktable's order (`src/common/iop_order.c`'s `v50_order` at the reference release), or the one `crates/operations/order.md`'s table gives it where Apertrust departs from darktable's place (decision 22); a new operation's place goes into that table, and a departure is an architecture decision. Then the domain, layer support from the Layers column of `docs/modules/README.md`, and the neighbourhood radius from the spec, or `Operation::reach` where it depends on the parameters or the scale (decision 13). A tile grows its input by the reaches of the operations in it, so a reach too small shows as differences at tile edges, which `crates/engine/tests/tiles.rs` catches. An operation that writes only part of its input, as demosaic writes the declared image, writes `image.region` of it: the whole image, or a tile's part (decision 13). `default_enabled` is on only for an operation an unedited photo must run, as darktable's scene-referred workflow runs it on an unedited raw; turning it on changes every photo's default render and the whole-pipeline test's (decision 28), and a test holds the set to decision 22's eight and colour calibration (decision 27) until a decision changes it. Off, the operation runs only while a module sets one of its parameters, so it needs no identity setting, and none of its parameters can be set or saved at operation level. Colour calibration's flag is on (decision 27), and the whole-pipeline test's history gives darktable the same instance. Colour balance rgb's stays off, as darktable has it (decision 32).
2. **The schema**, from the port spec's parameter table (decision 21): darktable's field names and ranges; darktable's scene-referred defaults where they differ from its introspection ones; version 1. Out-of-range values are rejected when set, so a range is a hard limit, not a slider's. darktable's older versions are decoded in the golden harness's `ports.rs` for the cases that hold them, and the import of darktable's edits will need every version darktable can store (decision 51, planned).
3. **The Slang source and `prepare`**, with the generated WGSL validated (`slang-kernels`).
4. **The owners**: which module owns each parameter, from the port spec's Owner column; that module lists it in `Module::owns` (decision 28). The module itself is `tool-bindings`' work.
5. **The tests**: a golden case, the gradient check, and invariant tests: finite output on extreme input, migrations rendering identically. A module that is off being a no-op, and one every photo runs being untouched at its defaults, is the module's test (`tool-bindings`; decision 32).
6. **Provenance**, copied from the port spec's header.

An operation no module needs, or a parameter with no owning module, is a product question for the user before it is code.
